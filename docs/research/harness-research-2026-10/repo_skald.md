## 1. Identity: what skald is, size, history, license, deployment, Saga references

### Takeaway
Skald is a Go, model-free, single-user Linux daemon, CLI and terminal UI. It archives native Claude Code, Codex and Devin conversation transcripts losslessly into SQLite and lets you browse them. It was written and published in one day (2026-09-10) as part of the operator's newer desktop ecosystem (its own Heimdall, Braid, dotprivate and WCU), it has no license, and it never mentions Saga, Bragi, Obsidian, a vault or lessons. Saga's role name "skald" is the only link.

## 2. Architecture and interfaces: inputs, outputs, model use, scheduling, incrementality, configuration

### Takeaway
Skald reads native agent transcripts (Claude Code `~/.claude/projects/**/*.jsonl`, Codex rollouts and Devin SQLite stores). It already parses Claude Code session transcripts, but only those three hard-coded provider formats. It writes only a private SQLite archive, backups and JSON/TUI reads over a same-user Unix socket. It never calls a model, by design. It polls continuously and incrementally with prefix-verified checkpoints and idempotent, transactional commits. It produces no Markdown, Obsidian files, git commits or lessons.

### Cited Findings
- **Inputs.** The default roots are `${CLAUDE_CONFIG_DIR:-~/.claude}/projects`, `${CODEX_HOME:-~/.codex}/sessions` and `${DEVIN_DESKTOP_CONFIG:-~/.config/Devin}/User/acp-messages`. "Browser/cloud conversations are not covered" — [docs/SOURCES.md L44-L48](https://github.com/algorhythmic/skald/blob/d364f8f3100d204b94122e4e3482027a7709d8c1/docs/SOURCES.md#L44-L48). Devin per-session SQLite stores are canonicalized to JSONL — [SOURCES.md L50-L55](https://github.com/algorhythmic/skald/blob/d364f8f3100d204b94122e4e3482027a7709d8c1/docs/SOURCES.md#L50-L55).
- **Providers are hard-coded.** `const ( Claude = "claude_code"; Codex = "codex"; Devin = "devin" )` and `validate()` returns `unsupported_provider` for anything else — [sessioncapture/capture.go L19-L24, L93-L95](https://github.com/algorhythmic/skald/blob/d364f8f3100d204b94122e4e3482027a7709d8c1/sessioncapture/capture.go#L19-L95). ### Inferences
- Skald is an L1 archive and L2 viewer. It is the raw-history layer under a chronicle, not a chronicle. The "description" it shows is the provider's own recap or a labelled excerpt, never a generated summary ([plan L563-L587](https://github.com/algorhythmic/skald/blob/d364f8f3100d204b94122e4e3482027a7709d8c1/SKALD-IMPLEMENTATION-PLAN.md#L563-L587)).
- Because it is model-free, it has none of Saga's billing constraints (`claude -p`, credentials volume). It could run natively on the Docker host VM like `heimdall.service`, outside any container.

## 3. Relationship to Saga's Bragi: lineage, additions, removals, survival of the compilation pass and lessons step, layout compatibility

### Takeaway
Skald does not supersede Bragi. The two overlap in only one value they share: verbatim, source-attributed preservation. Bragi's actual product is a model-compiled Obsidian vault with wiki-links, indexes, decision records, principles and a glossary, plus the cross-project lessons store. Skald has no equivalent of that product, and its design forbids the model calls that producing it requires. Bragi's compilation pass and step 3.5 do not survive in skald. `/opt/saga/vault` and `/opt/saga/lessons` neither conflict with skald nor are produced by it. At most, skald could become the raw-transcript substrate that a slimmer Bragi successor reads.

### Cited Findings
- **What Bragi is.** A Sonnet Claude Code session ("You are a compiler") that reads `/workspace/inputs/odin/{incoming-journals,outgoing-guidance/sent,incoming-alerts,master-journal.md,projects/*/wiki}` and `/workspace/inputs/mimir/{processed,verdicts}` — [bragi/CLAUDE.md L17-L39](../../../bragi/CLAUDE.md). It also reads the RO `saga-repo` and `dvergr-workspaces` — [bragi/CLAUDE.md L55-L81](../../../bragi/CLAUDE.md). It writes `/workspace/vault/` ("Obsidian-friendly … wiki-style links, a `.obsidian/` directory … your own git history") and `/workspace/lessons/` — [bragi/CLAUDE.md L41-L53](../../../bragi/CLAUDE.md).
- **Vault schema.** `README.md`, `index.md`, `log.md`, `projects/{project}/{index.md,dvergar/,journals/,guidance/,decisions/}`, `principles.md`, `glossary.md` and `decisions/` — [bragi/CLAUDE.md L87-L121](../../../bragi/CLAUDE.md).
- **Compilation pass.** Steps: detect new material by mtime against git log, read only new inputs, update pages and cross-link, step 3.5 distil lessons on project completion, regenerate `index.md`, commit `compile: …`, and emit `COMPILED` if there is no diff — [bragi/CLAUDE.md L123-L158](../../../bragi/CLAUDE.md). Lessons are one file per project per topic, `<topic>/<YYYY-MM-DD>-<project>-<slug>.md`, append-only with `supersedes`/`superseded-by` — [bragi/CLAUDE.md L160-L204](../../../bragi/CLAUDE.md). The rules are to quote verbatim, name the source, and never paraphrase — [bragi/CLAUDE.md L206-L227](../../../bragi/CLAUDE.md).
- **Runtime.** `FROM saga-devcontainer:base`, credentials volume, persona baked in, lessons template seeded — [containers/bragi/Dockerfile L19-L63](../../../containers/bragi/Dockerfile). The init script git-inits the vault, starts `claude --dangerously-skip-permissions` in tmux, sets effort `low`, installs `/ralph-loop`, and runs up to 10 iterations with the completion promise `COMPILED` — [containers/bragi/init-bragi.sh L124-L125, L170-L196, L211-L253](../../../containers/bragi/init-bragi.sh).
- **Scheduling is labelled "future".** The launcher's cron block is headed "Scheduling (future)" with an example `*/30 * * * *` — [scripts/auth/launch-bragi-template.sh L132-L143](../../../scripts/auth/launch-bragi-template.sh). ## 4. Fit with the Odin I/O contract: consuming the UniiChat-style log, adapter, emitting `note`, guidance-effectiveness join

### Takeaway
Skald cannot consume `chat/main/YYYY-MM-DD.jsonl` lines (`{i, kind, src, text, size, date, ref}`) as-is. Discovery rejects them, and explicit registration would archive every line as an opaque record. A small fourth provider adapter would fit well, because the log is append-only, single-writer, has dense permanent ids, and its tree nodes are exactly "summaries with explicit coverage". Skald cannot emit `note` messages back: it is read-only at the source, has no write API, and forbids model calls. The guidance-effectiveness join is not something skald computes, and the contract's "by `ref`" rule is under-specified as written.

### Cited Findings

### Inferences
- **Adapter sketch.** Add a fourth provider (say `saga_chat`) to `sessioncapture`, with `validate`/`Identify`/`normalize` branches:
  - native record ID = `i`, which is dense and permanent, so record keys are stable
  - `date` → `source_time`
  - `src` → `role`/`channel` and the provenance producer
  - `operator`/`odin`/`fleet`/`verdict`/`host`/`work` → `message`; `tool` → `tool_call`; `echo` → `tool_result`; `note` → `native_note`
  - `ref` → a `relations` entry with an evidence basis
  - each `chat/tree` node `{l, i, text}` → `native_summary` with `coverage` = the explicit `i` range it covers. This is a better fit than any provider skald supports today, because UniiChat summaries carry exact coverage.
  - `view.json` is rewritten in place and must not be captured.
- **Identity fix needed in the contract, not in skald.** Skald refuses filename-derived identity ([discovery.go L100-L101](https://github.com/algorhythmic/skald/blob/d364f8f3100d204b94122e4e3482027a7709d8c1/sessioncapture/discovery.go#L100-L101)), so each line (or a header line in each day file) should carry a conversation id such as `chat: "odin/main"` or `chat: "work/<name>"`. Otherwise day files are not self-identifying, and multi-agent logs (`chat/<agent>/…`) would be ambiguous.
- **Fit with skald's checkpoint model.** The contract's append-only, single-writer, flush-per-write rules match skald's prefix-verified tailing exactly. Any rewrite would surface as a new generation plus a gap, which is a useful integrity check on the log.
- **`note` emission must live outside skald.** A Bragi successor (still a model session) would read the JSONL directly or through skald, then write lessons via the harness's import endpoint. The contract names that endpoint only once (L317) and never specifies it; the one-time import in §11 is a different mechanism.
- **The guidance-effectiveness join as specified will not work "by `ref`".** Guidance publishes to `dvergr/p/i/guidance`, status transitions have no stated `ref`, and per-iteration status is never logged. A workable rule:
  1. The key is `(project, instance)`, taken from the `publish_guidance` `tool` line's JSON input, and from `src = dvergr/<p>/<i>` or the `[p/i]` prefix on `fleet` lines.
  2. The window is the subsequent `i` up to the next guidance to the same instance.
  3. The evidence is the `fleet` journal entries (logged whole) and the transition one-liners with their numbers.
  4. The "Outcome" verdict remains a model judgment, as in the old table.
  Alternatively, the contract should set `ref = "dvergr/<p>/<i>"` (or a guidance id) on the guidance `tool`/`echo` pair and on every `fleet` line. The `size` field also makes Bragi's verbosity-drop check deterministic (bytes per journal entry per instance).
- Skald adds nothing to this join today: there is no relations table and no query by `ref`, and `context.query` is unimplemented.

### Gaps
- Whether discovery's `duplicate_conversation_locator` rule would trip on several day files asserting one conversation id was not verified without running code.
- The contract does not specify the import endpoint's transport (drop directory, socket or HTTP), its authentication, or how `src = bragi` is enforced.
