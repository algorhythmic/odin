Research date: 2026-10-13. Current Claude Code release: **v2.1.299** (npm publish 2026-10-14 UTC; GitHub releases page shows "14 Oct", marked Latest). ## Q1. Hooks: complete event list, what each can do, and whether a hook can inject a message into a running session from outside

### Takeaway
As of v2.1.299 there are 33 documented hook events (the April-2026 list of ~9 has more than tripled), five handler types (`command`, `http`, `mcp_tool`, `prompt`, `agent`), and two background modes (`async`, `asyncRewake`). No hook is itself an external-injection API, but `asyncRewake` command hooks "wake Claude immediately even when the session is idle" on exit code 2, and `SessionStart` can watch paths and (in `-p`) supply the first user message — so hooks alone can replace a *file-marker + end-of-turn scan* but not a *send-keys* nudge. The primitives that genuinely replace send-keys are covered in Q2.

### Cited Findings
- Full event list on the hooks reference (lifecycle table): `SessionStart`, `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `MessageDisplay`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `Elicitation`, `ElicitationResult`, `SessionEnd` — [Official: Hooks reference](https://code.claude.com/docs/en/hooks)
- Which can block (exit 2 or a `decision` field): `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse` (`permissionDecision: allow/deny/ask/defer`, `updatedInput`), `PostToolBatch` (exit 2 stops the agentic loop), `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop` (prevents stopping, continues the conversation), `TeammateIdle`, `ConfigChange` (except `policy_settings`), `WorktreeCreate` (non-zero fails creation), `PreCompact` (blocks compaction), `PreModelSwitch`, `Elicitation`, `ElicitationResult`. Non-blocking: `SessionStart`, `Setup`, `PermissionRequest` ("exit 2 is not honored"; returns `hookSpecificOutput.decision.behavior`), `PermissionDenied` (`retry: true`), `PostToolUse` (exit 2 shows stderr to Claude; can `updatedToolOutput`), `PostToolUseFailure`, `Notification`, `MessageDisplay` (display-only `displayContent`), `SubagentStart`, `StopFailure`, `InstructionsLoaded`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeRemove`, `PostCompact`, `PostModelSwitch`, `SessionEnd` — [Official: Hooks reference](https://code.claude.com/docs/en/hooks)
- Context injection fields: `hookSpecificOutput.additionalContext` on `SessionStart`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `SubagentStart`, `SubagentStop`, `Stop`, `PostModelSwitch`. "Plain stdout and the `additionalContext` value are each injected as a system reminder that starts with the hook's name; Claude reads both." `systemMessage` is "shown to the user, not to Claude." `UserPromptSubmit` `additionalContext` "doesn't start a new turn. It's added to the prompt that's already being submitted." — [Official: Hooks reference](https://code.claude.com/docs/en/hooks)
- `SessionStart` output fields: `initialUserMessage` — "String used as the first user message of the session, in non-interactive mode with the `-p` flag. It becomes the first turn even if you pass no prompt. A prompt you do pass follows as the next turn"; `watchPaths` — "Array of absolute paths to watch for FileChanged events during this session"; `sessionTitle`; `reloadSkills`. `source` matcher values: `startup`, `resume`, `clear`, `compact`, `fork`. Resume-input fields (`seconds_since_last_response`, `context_tokens`) require v2.1.251+ — [Official: Hooks reference](https://code.claude.com/docs/en/hooks)
- `FileChanged` (added v2.1.83, with `CwdChanged`): fires when a watched file changes on disk "whatever wrote it"; input has `file_path` and `event`; "FileChanged hooks have no decision control. They can't block the file change from occurring." Output supports `watchPaths` and `systemMessage` only; "The message doesn't reach the SDK message stream." — [Official: Hooks reference](https://code.claude.com/docs/en/hooks); [Official: CHANGELOG 2.1.83](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)
- `Stop` hook: `decision: "block"` "prevents Claude from stopping"; `reason` is "Required when `decision` is `"block"`. Tells Claude why it should continue." Loop guard: `stop_hook_active` input field, and "after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn" (counter resets on tool use; `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises it). Stop input also carries `last_assistant_message` and `session_crons` (pending `/loop` wakeups) — [Official: Hooks reference](https://code.claude.com/docs/en/hooks); [Official: Tools reference, ScheduleWakeup row](https://code.claude.com/docs/en/tools-reference)
- Handler types: `command` (shell; `args` exec form; `shell: bash|powershell`), `http` (POST event JSON to `url`, added v2.1.63), `mcp_tool` (calls `server`/`tool`, added v2.1.118), `prompt` (single-turn model evaluation), `agent` ("spawns a subagent that can use tools to verify conditions", experimental). Common fields: `if`, `timeout`, `statusMessage`, `once`, and `onFailure: "block"` (v2.1.295+) — [Official: Hooks reference](https://code.claude.com/docs/en/hooks)
- Background hooks: "`async: true` (command hooks) runs in the background without blocking. Claude Code doesn't enforce `timeout` on these." "`asyncRewake: true` runs in the background and wakes Claude on exit code 2. Stderr, or stdout if stderr is empty, is delivered to Claude as a system reminder." "Claude Code still enforces `timeout` on a hook you run with `asyncRewake`." Limitation: "Hook output is delivered on the next conversation turn. If the session is idle, the response waits until the next user interaction. Exception: an `asyncRewake` hook that exits with code 2 wakes Claude immediately even when the session is idle." In `-p`, "Claude Code kills any async hook still running at teardown" — [Official: Hooks reference](https://code.claude.com/docs/en/hooks)
- Hooks and `/goal`: "`/goal` is a wrapper around a session-scoped prompt-based Stop hook"; a Stop hook "lives in your settings file, applies to every session in its scope, and can run a script for deterministic checks or a prompt for model-evaluated ones." — [Official: /goal](https://code.claude.com/docs/en/goal)
- No general external API: "The visible content describes no general external API for pushing messages into a live session... HTTP hooks are request/response, so they can't push messages unprompted." (WebFetch summary of the hooks reference; the inbox socket and mods API documented in Q2 are the external paths) — [Official: Hooks reference](https://code.claude.com/docs/en/hooks)
- Hook events added since the April-2026 baseline (dates from npm): `PermissionDenied` (2.1.89), `TaskCreated` (2.1.84), `PreCompact` blocking (2.1.105, ~Apr 13), `MessageDisplay` (2.1.152, ~May 26), `DirectoryAdded` (2.1.219, ~Jul 23), `PreModelSwitch`/`PostModelSwitch` (2.1.251, ~Aug 27), `UserPromptSubmit` now runs before skill/command expansion (2.1.299). Pre-April additions: `CwdChanged`/`FileChanged` (2.1.83), `StopFailure` (2.1.78), `Elicitation`/`ElicitationResult`/`PostCompact` (2.1.76), `InstructionsLoaded` (2.1.69), `ConfigChange` (2.1.49), `WorktreeCreate`/`WorktreeRemove` (2.1.50), `TeammateIdle`/`TaskCompleted` (2.1.33), `Setup` (2.1.10) — [Official: CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)

### Inferences
- A Saga-style "marker file dropped by sidecar, scanned at end of turn" can be replaced by `SessionStart` returning `watchPaths` + a `FileChanged` command hook — but `FileChanged` cannot inject context or start a turn (only `systemMessage`/`watchPaths`), so it only helps if Odin is mid-turn and the hook writes state the model later reads. It does not wake an idle Odin.
- The one hook-only path that wakes an idle session is `asyncRewake` exit-2. Because `timeout` is still enforced on `asyncRewake` hooks, a long-lived MQTT subscriber must be re-armed each turn (for example, a `Stop` or `UserPromptSubmit` hook spawning an `asyncRewake` `mosquitto_sub -C 1` with a generous timeout). The default hook timeout value was not captured in these notes; verify before relying on it.
- `PostToolBatch` exit-2 and `Stop` `decision: "block"` give deterministic per-turn control equivalent to what the `/ralph-loop` Stop-hook plugin does; `/goal` is the first-party packaging of the same mechanism.

### Gaps
- The exact default `timeout` for command hooks and whether `asyncRewake` can exceed it was not extracted (the relevant paragraph was in a page region not read).
- Whether `initialUserMessage` has any effect in interactive sessions is not documented (the field is defined only for `-p`).

## Q2. Primitives that can push an external event into a running interactive session (the tmux-send-keys replacement question)

### Takeaway
As of October 2026 there are **four official in-process ways** to deliver an externally-originated message to a running interactive Claude Code session without keystrokes: (1) the per-session **inbox Unix socket** (`CLAUDE_CODE_MESSAGING_SOCKET`, cross-session messaging, v2.1.224+, Aug 2026) which Claude Code explicitly says "a script or hook" can post into and which "starts a new turn with the message" when the session is idle; (2) a **mod** (plugin JS running inside Claude Code, v2.1.287+, Oct 2026) that can `$.process.spawn` a long-lived subscriber and call `$.prompt.submit({ text, asUser })` which "waits until the session is idle and then starts a new turn"; (3) a **channel** MCP server (`claude/channel` capability, research preview since v2.1.80, March 2026) whose `notifications/claude/channel` events arrive as `<channel>` tags; (4) the **Monitor tool / plugin monitors** which stream each stdout line or WebSocket message back to Claude as events. All of these are same-machine (same container) mechanisms; none crosses a container boundary by itself.

### Cited Findings
- Inbox socket exists per session: "Claude Code binds an inbox socket for each session with cross-session messaging enabled, where other sessions on the machine deliver messages. The socket is a Unix domain socket on macOS and Linux... Read this section when... you want a script or hook to post into a session". Path exported as `CLAUDE_CODE_MESSAGING_SOCKET` "before any hook runs, including `SessionStart`"; `/status` shows it in the `Peer address` row prefixed `uds:`; default directory `/tmp/cc-socks-<uid>` — [Official: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Delivery semantics: "The receiving Claude reads the message between tool calls during an active turn, so a running tool is never interrupted. When the receiving session is idle, Claude Code starts a new turn with the message." "A message from another session arrives as plain text." — [Official: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Auth line for scripts: "A script posting to its own session's socket can send `{"type":"auth","token":"<token>"}` as the first line of its connection, where `<token>` is the value of `CLAUDE_CODE_MESSAGING_TOKEN`... macOS and Linux: the line is optional." "Claude Code closes a connection that hasn't sent a complete line within 30 seconds." Own-child messages (a hook or Bash command posting back) are delivered without approval when no `crossSessionInbound` value applies; "in a container where Claude Code runs as process ID 1 it has no process evidence at all" and then relies on the token — [Official: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Trust/approval: "When session A messages session B, Claude Code tells B's Claude that the message came from another session, not from you... It can't approve anything... Commands don't run." With no `crossSessionInbound` setting, a receiver that bypasses permissions "holds each message for your approval" unless the sender also bypasses; set `crossSessionInbound: accept` to deliver unattended; "Claude Code holds at most 100 messages". Message loops are throttled; same-machine size cap ~1M chars — [Official: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Container boundary: "A session inside a container and a session on the host can't reach each other. Two sessions inside the same container can still message each other, including on a self-hosted runner." Cross-machine messaging "Through Anthropic servers, arriving over that machine's Remote Control connection" (requires claude.ai sign-in; not with API key or cloud providers) — [Official: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- `-p` workers can receive: "Claude Code binds an inbox socket for a `claude -p` session like an interactive one, so a long-running `-p` worker can receive messages and appears in the listing"; bare mode doesn't bind it. "To let a `-p` worker take messages unattended, start it with `crossSessionInbound` set to `accept` in its `--settings` value." — [Official: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Usage accounting: "Once delivered, the message counts toward usage like a prompt you type" — [Official: Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Mods can inject prompts: a mod "can... rewrite a prompt or a tool call, submit a prompt as if you had typed it, or send a message to another of your sessions" — [Official: Mods overview](https://code.claude.com/docs/en/plugins/mods/overview). "When a background job finds something that needs Claude's attention, it can start a turn by submitting a prompt with `$.prompt.submit({ text })`. Claude reads the text after a sentence that names your mod as the sender. To send it as the user's own words, without that sentence, add `asUser: true`. The call waits until the session is idle and then starts a new turn." — [Official: Mods API](https://code.claude.com/docs/en/plugins/mods/api)
- Mods can hold long-lived processes/timers: "`$.clock.every` and `$.clock.after` take the place of `setInterval` and `setTimeout`"; "The timer's callback runs outside any event, so it keeps running between turns and doesn't start one." `$.process.run([...])` (30 s default timeout) and "`spawn` streams a long-running command's output." `$.http.fetch`, `$.fs.*`, `$.store` (persisted KV), `$.mcp.call`, `$.session.send({ to: { sessionId }, text })` "makes the same delivery the SendMessage tool makes." `session.receive` hook lets a mod observe inbound messages and `{ consumed: reason }` them. "Timers stop when the module reloads." The hooks module "has no Node.js APIs, no timer globals such as `setTimeout`, and no network or file access of its own" except via `$` — [Official: Mods API](https://code.claude.com/docs/en/plugins/mods/api)
- Where mods run: hooks run in terminal, Desktop Code tab, VS Code chat panel, `claude -p` and the Agent SDK, Remote Control, and cloud sessions; drawing only in terminal/Desktop. Mods require v2.1.287+ (terminal); "Mods aren't sandboxed"; `--safe-mode` or `disableAllHooks` turns them off. 2.1.299 changelog: "`session.append` gained a `queue` door" and `turn.start` fires for subagents/teammates — [Official: Mods overview](https://code.claude.com/docs/en/plugins/mods/overview); [Official: CHANGELOG 2.1.299](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)
- Channels deliver into the running session: "A channel is an MCP server that pushes events into your running Claude Code session"; "Events only arrive while the session is open"; events "queue into the session and are processed in order. If several notifications arrive while Claude is busy, they're delivered together on the next turn and Claude handles them as a group." — [Official: Channels](https://code.claude.com/docs/en/channels); [Official: Channels reference](https://code.claude.com/docs/en/channels-reference) (full channel detail in Q3)
- Monitor tool: "Runs a command in the background and feeds each output line back to Claude... Can also open a WebSocket and treat each incoming message as an event." "Every watch Claude starts has a deadline: 5 minutes by default, at most 30 minutes, and at most 10 minutes in a non-interactive run"; "At the deadline the watch ends. Claude gets one notice, so it can start the watch again if it's still needed." Not available on Bedrock/Vertex/Foundry or with `DISABLE_TELEMETRY`/`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`. WebSocket watches deny private/link-local addresses — [Official: Tools reference, Monitor tool](https://code.claude.com/docs/en/tools-reference)
- Plugin monitors (manifest `experimental.monitors`, added as top-level `monitors` in 2.1.105): "A monitor is a shell command that runs in the background for the whole session. What it prints reaches Claude as notifications"; "Interactive sessions only: plugin monitors start in an interactive session and never in non-interactive mode with the `-p` flag"; run "with your full user permissions and outside the sandbox" — [Official: Plugin components, Monitors](https://code.claude.com/docs/en/plugins/components); [Official: Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Scheduled wakeups: `/loop` + `CronCreate`/`CronList`/`CronDelete` (2.1.71); "A scheduled prompt fires between your turns, not while Claude is mid-response"; "Tasks only fire while Claude Code is running and idle"; self-paced loops may use Monitor instead of polling; recurring tasks expire after 7 days; max 50 per session — [Official: Scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Background-session reply path (no CLI send command): agent view supports a "Peek reply" (select row, `Space`, type, `Enter`); "While a session is working, replies join its message queue instead of interrupting it". "The page doesn't document a `claude send` command." `claude --resume <session-id> --bg "prompt"` (v2.1.257+): "Claude Code continues that session under its own ID, or starts a copy under a new ID and prints a `note:` line explaining why." — [Official: Agent view](https://code.claude.com/docs/en/agent-view)
- Routines API trigger (cloud, not local): POST to `https://api.anthropic.com/v1/claude_code/routines/<id>/fire` with a per-routine bearer token starts a *new* cloud session; `text` arrives wrapped in a `<routine-fire-payload>` block labeled untrusted — [Official: Routines](https://code.claude.com/docs/en/routines)

### Inferences
- The closest first-party drop-in for Ratatoskr's `tmux send-keys` is the inbox socket: a Python sidecar in Odin's container can connect to `$CLAUDE_CODE_MESSAGING_SOCKET`, send the auth line, and post a message; with `crossSessionInbound: accept` in Odin's settings, the message starts a new turn when Odin is idle and is read between tool calls otherwise. The receiving model is told the text "came from another session, not from you" and it "can't approve anything" — acceptable for guidance/journal events, but Telegram operator commands should keep coming through the channel plugin (which already arrives as user-like `<channel>` events).
- A mod is the most capable option (it can own an MQTT subscription via `$.process.spawn`, call `$.prompt.submit({asUser:true})`, keep a `$.store`, and even add Odin-side `/commands`), at the cost of trusting JS that runs inside the Claude Code process and of being only ~2 weeks old (v2.1.287 shipped 2026-10-01).
- Because none of these cross a container boundary, the MQTT broker (or Heimdall's filesystem) remains the right transport *between* containers; the primitives above only remove the keystroke hack *inside* each container.

### Gaps
- The wire format of a message line on the inbox socket (beyond the optional `{"type":"auth",...}` first line) is not in the public docs; community posts describe only the auth line and the plain-text payload. It would need to be derived from the Claude Code binary or by capturing a SendMessage. Treat as undocumented/unstable.
- No official document states whether a mod's `$.prompt.submit` works when Claude Code is running inside Docker as PID 1 (mods docs make no container-specific exception; cross-session docs do).

## Q3. Channels (`--channels`): how custom channel plugins work, third-party MCP-as-channel, permission model, first-party channels

### Takeaway
Channels are still a research preview (shipped v2.1.80, 2026-03-19). Any MCP server that declares the `claude/channel` experimental capability and emits `notifications/claude/channel` becomes a channel, so an MQTT bridge is a ~40-line Bun/Node script — but during the preview only allowlisted plugins register via `--channels`; a custom channel needs `--dangerously-load-development-channels`, which shows an interactive full-screen confirmation and is **ignored in `-p`/SDK mode**. Pro/Max users cannot add their own plugin to the allowlist (only Team/Enterprise admins can via `allowedChannelPlugins`). First-party channels: Telegram, Discord, iMessage, plus the fakechat demo; no Slack channel (Slack is a separate cloud-session integration).

### Cited Findings
- Definition and status: "Channels are in research preview. They require Anthropic authentication through claude.ai or a Console API key, and are not available on Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry." "Telegram, Discord, and iMessage are included in the research preview." "Neither `--channels` nor `--dangerously-load-development-channels` appears in `claude --help` while the feature is in preview." — [Official: Channels](https://code.claude.com/docs/en/channels)
- Contract: server must "Declare the `claude/channel` capability" (`capabilities.experimental['claude/channel']: {}`), "Emit `notifications/claude/channel` events", and "Connect over stdio transport". Params: `content` (string body) and `meta` (string map; keys must be identifiers, others "silently dropped"). The model receives `<channel source="<server>" k="v">...</channel>`; `source` is set from the server's configured name (`plugin:<name>:<server>` for plugins). `instructions` in the Server constructor is delivered to Claude as context — [Official: Channels reference](https://code.claude.com/docs/en/channels-reference)
- No acknowledgement: "Claude Code doesn't acknowledge notifications... If the session hasn't loaded your server as a channel, or the organization policy blocks it, Claude Code drops the events silently"; queued events "are delivered together on the next turn" — [Official: Channels reference](https://code.claude.com/docs/en/channels-reference)
- Replies: a two-way channel exposes a normal MCP tool (e.g. `reply`) and `capabilities.tools: {}`; "When Claude replies through a channel, you see the inbound message in your terminal but not the reply text" — [Official: Channels](https://code.claude.com/docs/en/channels); [Official: Channels reference](https://code.claude.com/docs/en/channels-reference)
- Permission relay: declare `capabilities.experimental['claude/channel/permission']: {}`; Claude Code sends `notifications/claude/channel/permission_request` (`request_id` of five lowercase letters without `l`, `tool_name`, `description`, `input_preview`), the server replies `notifications/claude/channel/permission` with `request_id` and `behavior: 'allow'|'deny'`. Since v2.1.234 relay goes only to servers registered as channels. Credentials masked `[REDACTED]` from v2.1.234. "Project trust and MCP server consent dialogs don't relay" — [Official: Channels reference](https://code.claude.com/docs/en/channels-reference)
- Allowlist/preview gate: "During the preview, `--channels` only accepts plugins from an Anthropic-maintained allowlist, or from your organization's allowlist if an admin has set `allowedChannelPlugins`"; "A channel published to your own marketplace still needs `--dangerously-load-development-channels` to run"; "The community marketplace is not on the channel allowlist." "Pro and Max users without an organization skip these checks entirely: channels are available and users opt in per session with `--channels`" (i.e. they get the Anthropic default list) — [Official: Channels](https://code.claude.com/docs/en/channels); [Official: Channels reference](https://code.claude.com/docs/en/channels-reference)
- Dev flag is interactive-only: "Claude Code first shows a full-screen warning dialog listing the development channels you're loading. Select **I am using this for local development** to continue". "Run the development flag in an interactive session, where Claude Code can show the confirmation prompt. If you pass it in non-interactive mode with `-p` or through the Agent SDK, Claude Code ignores the flag and the channel doesn't register." Forms: `plugin:<name>@<marketplace>` or `server:<name>` (bare `.mcp.json` server) — [Official: Channels reference](https://code.claude.com/docs/en/channels-reference)
- Headless behaviour: "When you run channels in non-interactive mode with `-p`, tools that need terminal input, such as multiple-choice questions and plan mode approval, are disabled so the session never stalls waiting for input." "For unattended use, `--dangerously-skip-permissions` bypasses most prompts" — [Official: Channels](https://code.claude.com/docs/en/channels)
- Security model: "Every approved channel plugin maintains a sender allowlist"; Telegram/Discord pair via a code (`/telegram:access pair <code>`, then `/telegram:access policy allowlist`); "Being in `.mcp.json` isn't enough to push messages: a server also has to be named in `--channels`." "An ungated channel is a prompt injection vector... Gate on the sender's identity, not the chat or room identity" — [Official: Channels](https://code.claude.com/docs/en/channels); [Official: Channels reference](https://code.claude.com/docs/en/channels-reference)
- Plugin packaging: manifest `channels: [{ server, displayName, userConfig }]` bound to one of the plugin's `mcpServers`; Telegram plugin stores the token at `~/.claude/channels/telegram/.env` or reads `TELEGRAM_BOT_TOKEN`; invoke with `claude --channels plugin:telegram@claude-plugins-official`; multiple plugins may be passed space-separated — [Official: Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference); [Official: Channels](https://code.claude.com/docs/en/channels)
- MCP v2 runtime caveat: "On the v2 MCP client runtime, a channel can also fail to register because Claude Code doesn't register a channel server that negotiates protocol revision 2026-07-28"; stdio servers negotiate that revision by default from v2.1.292, so a channel server may need `MCP_PROTOCOL_NEGOTIATION=legacy` — [Official: Channels](https://code.claude.com/docs/en/channels); [Official: MCP](https://code.claude.com/docs/en/mcp)
- Comparison table on the channels page lists Cloud sessions, Claude in Slack (spawns a cloud session from an `@Claude` mention), standard MCP, and Remote Control; "Channels fill the gap... by pushing events from non-Claude sources into your already-running local session." — [Official: Channels](https://code.claude.com/docs/en/channels)
- Changelog: `--channels` research preview (2.1.80); permission relay (2.1.81); `allowedChannelPlugins` (2.1.84); `--channels` works with Console API-key auth (2.1.128) — [Official: CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)

### Inferences
- An MQTT→channel bridge is technically trivial (subscribe with paho/mosquitto, call `mcp.notification({method:'notifications/claude/channel', params:{content, meta:{topic, dvergr}}})`), and arrives as a user-turn-like `<channel>` event, which is exactly the delivery semantics Saga wants. The blocker for unattended operation is the preview allowlist: an Odin container on a Pro/Max plan would have to dismiss the `--dangerously-load-development-channels` dialog at every start (one send-keys at boot, which is the kind of dialog the operator found unscriptable for `.claude.json` onboarding), or the operator would need a Team/Enterprise org to allowlist the plugin.
- The Telegram plugin already in use is unchanged in kind (still a Bun stdio MCP channel) and remains the right operator interface; it also gives remote permission approval via relay if Odin ever runs without `--dangerously-skip-permissions`.

### Gaps
- Not found: any public timeline for channels leaving research preview or for opening the allowlist to custom plugins on Pro/Max.
- Not verified: whether the dev-channel confirmation dialog persists its answer (the docs say the flag "bypasses the allowlist for specific entries after a confirmation prompt", with no mention of remembering it).

## Q4. MCP servers in Claude Code: transports, tool search/deferred tools, resources, server push, sidecar patterns

### Takeaway
MCP in Claude Code (Oct 2026) supports stdio/http/sse(deprecated)/ws transports, defers tool definitions by default via tool search, honours `list_changed`, elicitation (incl. URL-mode), and a new v2 client runtime on MCP SDK 2.0 / protocol 2026-07-28. The only server-initiated path that reaches the *model* unprompted is the channel notification (Q3); ordinary notifications update tool lists but don't start turns. Long-running stdio servers are supported (tool calls >2 min auto-background; idle timeout 30 min for stdio), which is the documented "sidecar" shape.

### Cited Findings
- Transports: stdio (`claude mcp add <name> -- <cmd>`), `--transport http` (recommended remote; since v2.1.265 tries HTTP then falls back to SSE), `sse` (deprecated), `ws` (JSON-only via `.mcp.json`/`claude mcp add-json`). - Tool search: "MCP tool definitions are deferred by default, so only tool names and server instructions enter context until Claude uses a specific tool." `ENABLE_TOOL_SEARCH=false` disables; `alwaysLoad` server option (2.1.121) exempts a server; MCP tool description cap changed to 4,096 chars (2.1.296) — [Official: Costs](https://code.claude.com/docs/en/costs); [Official: MCP](https://code.claude.com/docs/en/mcp); [Official: CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)
- Server→client notifications: "An MCP server can change the tools, prompts, or resources it offers while connected and send a `list_changed` notification. In interactive sessions, Claude Code refetches the list. In `-p` mode and the Agent SDK, only the tool list is refreshed." Channel push: "An MCP server can also push messages directly into your session... The server declares the `claude/channel` capability. You opt in at startup with the `--channels` flag." — [Official: MCP](https://code.claude.com/docs/en/mcp)
- v2 runtime: "v1 uses MCP TypeScript SDK 1.x. v2 uses MCP TypeScript SDK 2.0, which adds MCP protocol revision 2026-07-28." ## Q6. Subagents and Agent Teams: mechanics, cross-machine capability, billing

### Takeaway
Agent Teams (experimental, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) are one lead session plus teammate sessions **on the same machine** (in-process or tmux/iTerm2 split panes), coordinating through a file-backed mailbox (`~/.claude/teams/<team>/inboxes/*.json`) and task list (`~/.claude/tasks/<team>/`). `TeamCreate`/`TeamDelete` tools were removed in 2.1.178; teammates spawn when the lead calls the Agent tool with a `name`. Teams cannot spawn in `-p`/SDK sessions, can't nest, and the lead is fixed. Teammates "count toward the same usage limits as your main conversation" on a subscription. Nothing in the docs supports teammates in separate containers; cross-container coordination is explicitly the cross-session-messaging + Remote Control path (Q2), which routes through Anthropic servers.

### Cited Findings
- Enablement/status: "Agent teams are experimental and disabled by default. Enable them by setting `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`"; "Spawning teammates also requires an interactive session. In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates" — [Official: Agent teams](https://code.claude.com/docs/en/agent-teams)
- How teams start: "Claude launches a teammate when it calls the Agent tool with a `name` while agent teams are enabled, unless the call is a fork or passes `isolation`"; "Every session gets an implicit team, so teammates spawn via the Agent tool's `name` parameter (2.1.178)"; "2.1.178 removed the TeamCreate and TeamDelete tools" — [Official: Agent teams](https://code.claude.com/docs/en/agent-teams); [Official: CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)
- Architecture: team lead, teammates ("Separate Claude Code instances"), task list, mailbox. "Each agent's mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`"; team config `~/.claude/teams/{team-name}/config.json` ("don't edit it by hand or pre-author it"); task list `~/.claude/tasks/{team-name}/` persists; "Task claiming uses file locking" — [Official: Agent teams](https://code.claude.com/docs/en/agent-teams)

- Messaging: `SendMessage` to one teammate by name; "To reach everyone, send one message per recipient"; idle notifications carry the teammate's final answer; a message "wakes an in-process teammate that is waiting to retry a failed API request" — [Official: Agent teams](https://code.claude.com/docs/en/agent-teams)

- Task tools availability: "`TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`, and `TodoWrite`, are available by default only on Opus 4.7, Sonnet 4.6, Haiku 4.5, and earlier models" (opt in elsewhere via `--allowedTools TaskCreate`); agents without them "coordinate through messages instead of the shared task list" — [Official: Tools reference](https://code.claude.com/docs/en/tools-reference); [Official: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Limitations (verbatim headings): "No session resumption with in-process teammates", "Task status can lag", "Shutdown can be slow", "One team per session", "No nested teams", "No background subagents from in-process teammates", "Lead is fixed", "Permissions set at spawn", "Split panes require tmux or iTerm2" — [Official: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Permissions: "Teammates start with the lead's permission mode... If the lead runs with `--dangerously-skip-permissions`, all teammates do too"; "Teammate permission prompts appear in the lead session"; plan approvals are auto-granted by the lead; messages between agents can't approve anything — [Official: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Cost/billing: "Agent teams use significantly more tokens than a single session"; "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode"; "An in-process teammate's requests fall outside the main conversation's cache TTL bucket, so its cache holds for five minutes by default, including on a Claude subscription" — [Official: Agent teams](https://code.claude.com/docs/en/agent-teams); [Official: Costs](https://code.claude.com/docs/en/costs)

### Inferences
- Agent Teams map onto Odin+dvergar only if every dvergr shares Odin's container (and user home), because the mailbox/task list are local files and spawning is the lead's Agent tool. That conflicts with Saga's per-dvergr container isolation and Heimdall boundary. Teams also lack per-teammate permission modes and session resumption, both of which Saga's long-running loops need.
- The team task list and mailbox are plain JSON on disk; a sidecar could in principle write to a teammate inbox, but docs warn the config is runtime state and messages are validated — not a supported integration surface.

### Gaps
- Not found: any official statement on running teammates on remote hosts; the only cross-machine primitive is cross-session messaging via Remote Control (Q2).

## Q7. Workflows, background sessions/Monitor, scheduled tasks, routines, Remote Control, Claude Code on the web/Projects, self-hosted environments, Managed Agents, FleetView — which are first-party planner+worker-pool replacements

## Q13. Anthropic engineering guidance on harnesses: recommended patterns

### Takeaway
Anthropic's published harness guidance (Sep 2025 → Jun 2026) converges on: separate the agent doing work from the agent judging it; give fresh-context workers a structured handoff (feature list as JSON, progress file, git history, init script); verify end-to-end before marking done; keep the simplest harness that the model can't do alone; and, since June 2026, let Claude write the orchestration script itself (dynamic workflows) using fan-out/synthesize, adversarial verification, generate-and-filter, tournament, classify-and-act, and loop-until-done patterns.

### Cited Findings
- "Effective harnesses for long-running agents" (2025-11-26, Justin Young): initializer agent vs coding agent split ("a different prompt for the very first context window"); feature list as JSON "all features initially marked failing", coding agents may only change `passes` ("It is unacceptable to remove or edit tests"); `claude-progress.txt`; "Agents commit with descriptive messages"; `init.sh`; self-verification via browser automation; "Choose a single feature to start working on"; "Compaction alone was insufficient"; 200+ features in the claude.ai clone example — [Official: anthropic.com/engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- "Harness design for long-running application development" (2026-03-24, Prithvi Rajasekaran): planner/generator/evaluator; "Separating the agent doing the work from the agent judging it proves to be a strong lever"; sprint contracts agreed before coding; "Each criterion had a hard threshold, and if any one fell below it, the sprint failed"; context resets needed "a structured handoff" and were essential for Sonnet 4.5's "context anxiety", dropped with Opus 4.5 in favour of auto-compaction; cost: solo run 20 min/$9 vs full harness 6 h/$200; "every component in a harness encodes an assumption about what the model can't do on its own"; "find the simplest solution possible, and only increase complexity when needed" — [Official: anthropic.com/engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- "A harness for every task: dynamic workflows in Claude Code" (2026-06-02, Thariq Shihipar & Sid Bidasaria): "Claude can now write its own harness on the fly"; three failure modes motivating it — agentic laziness, self-preferential bias ("prefer its own results... especially when asked to verify or judge them"), goal drift ("Each summarization step is lossy"); six patterns: classify-and-act, fan-out-and-synthesize ("The synthesize step is a barrier"), adversarial verification, generate-and-filter, tournament, loop until done; "barring the agents that read untrusted public content from taking high-privilege actions"; pair with `/loop` and `/goal`; "parallelism and specialization have to earn their coordination cost" — [Official: claude.dev blog](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- "Building agents with the Claude Agent SDK" (2025-09-29): "gather context -> take action -> verify work -> repeat"; agentic search first; file system as context; subagents with isolated context; compaction; "The best form of feedback is providing clearly defined rules for an output, then explaining which rules failed and why"; LLM-as-judge is "less robust and adds latency" — [Official: claude.com blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- "Effective context engineering for AI agents" (2025-09-29): "Context is a critical but finite resource"; just-in-time retrieval with lightweight identifiers; compaction; structured note-taking (NOTES.md); sub-agent architectures returning condensed summaries; "find the smallest set of high-signal tokens" — [Official: anthropic.com/engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Other 2026 engineering posts relevant to harnesses (titles/dates from the index; not fetched): "Scaling Managed Agents: Decoupling the brain from the hands" (2026-04-08), "How we built Claude Code auto mode: a safer way to skip permissions" (2026-03-25), "Building a C compiler with a team of parallel Claudes" (2026-02-05), "How we contain Claude across products" (2026-05-25) — [Official: anthropic.com/engineering index](https://www.anthropic.com/engineering)
- Docs cross-reference: the Agent SDK overview links the dynamic-workflows post as "Agent harness design: how the Claude Code team uses dynamic workflows to orchestrate many subagents at once" — [Official: Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### Inferences
- Saga's Odin/Mimir split (worker vs cross-model auditor) is exactly the generator/evaluator separation Anthropic recommends; the recommended state substrate (JSON feature list + progress file + git) matches Saga's journal design. The newer guidance adds two things Saga lacks: an explicit per-worker structured handoff contract and adversarial verification of worker outputs before the planner trusts them.

### Gaps
- "Scaling Managed Agents" and the C-compiler post were not read; their specific orchestration recommendations are not captured here.
