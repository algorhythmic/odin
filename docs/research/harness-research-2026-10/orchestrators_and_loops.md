# Orchestrators and Ralph-loop frameworks: the October 2026 landscape versus Saga's seven patterns

Research date: 2026-10-13. Scope: planner-over-worker-pool coding orchestrators and Ralph-loop derivatives, with per-system architecture notes and a synthesis of recurring patterns. Primary sources (READMEs, specs, vendor docs, authors' own posts) preferred; secondary coverage flagged. Items that could not be confirmed are listed under Gaps.

Saga's seven patterns, for reference: (1) planner (Odin) + cross-model auditor (Mimir) + worker pool (dvergar) under a single decider; (2) file-based handoff for binding decisions (request/verdict/marker files); (3) MQTT pub/sub for liveness/status; (4) deterministic gatekeeper daemon (Heimdall) outside the agent trust boundary; (5) per-agent self-written journals + evolving "principles"; (6) healer agent (Eir) turning deficiencies into PRs gated by auditor + human; (7) async human operator over Telegram. Workers run Claude Code `/ralph-loop` in Docker; planner writes per-worker PRDs with verbatim contracts.

## KQ0: Per-system architecture notes and current status (October 2026)

### Takeaway
The field has split into three tiers: (a) first-party vendor surfaces (Claude Code agent teams/agent view/Projects/routines/workflows, Codex cloud + Symphony, Devin "managed Devins", Cursor cloud agents, Copilot coding agent + Agent HQ), (b) open-source "N agents in worktrees" managers (Claude Squad, Conductor, Vibe Kanban, Superset, Crystal, dozens more), and (c) opinionated multi-role orchestrators (Gas Town/Gas City, Paperclip, claude-flow/Ruflo, ralph-orchestrator). The most famous of tier (c), Gas Town, was declared dead by its author in August 2026; the Ralph loop itself has been absorbed into first-party tooling (Claude Code's official plugin, `/loop`, `/goal`, Codex's "Ralph Wiggum Loop" reference in OpenAI's harness post).

#### OpenAI Symphony, Codex harness posts, Codex cloud

#### Ralph lineage
- Origin: "Ralph Wiggum as a 'software engineer'", 14 Jul 2025: "while :; do cat PROMPT.md | claude-code ; done"; "the technique is deterministically bad in an undeterministic world"; "future loops will not have the reasoning in their context window"; specs "one per file, in the specifications folder", plan in `fix_plan.md`; "Each time Ralph does something bad, Ralph gets tuned - like a guitar"; "You want to program in ways where Ralph can loop himself back into the LLM for evaluation" — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- "everything is a ralph loop" (17 Jan 2026): "Ralph works autonomously in a single repository as a single process that performs one task per loop"; explicitly monolithic, "not a set of multiple agents communicating with each other"; "that pattern is GENERIC and can be used for ALL TASKS"; "It's important to watch the loop"; Gas Town described as "a full level 8" orchestration — [ghuntley.com/loop](https://ghuntley.com/loop/)
- HumanLayer history (Jan 6, 2026): July 2025 loop was `while :; do cat PROMPT.md | npx --yes @sourcegraph/amp ; done`; Dec 2025 "Anthropic releases an official ralph wiggum plugin. - Register coverage Jan 27 2026 of Huntley's ~US$10/hour-of-compute claim — [The Register](https://www.theregister.com/2026/01/27/ralph_wiggum_claude_loops/); Huntley's May 2026 recap says the loop is "now incorporated in many, many tools" — [ghuntley.com/eighteen-month-recap](https://ghuntley.com/eighteen-month-recap/)

#### Claude Code first-party multi-agent surfaces (docs current to v2.1.2xx)
- Five surfaces: subagents; agent view (`claude agents`, research preview); agent teams ("Experimental and disabled by default"); Projects ("Public beta on Pro and Max"); dynamic workflows. "In every approach the workers are Claude sessions. To involve a different tool, expose it to Claude as an MCP server." Agent teams "don't isolate teammates in worktrees"; `/batch` splits a change into 5–30 worktree-isolated subagents; routines run on a schedule in the cloud — [code.claude.com/docs/en/agents](https://code.claude.com/docs/en/agents)
- Agent teams: enable with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; lead + teammates + shared task list + mailbox; mailbox is "a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`"; task list at `~/.claude/tasks/{team-name}/`; "Task claiming uses file locking"; tasks have pending/in progress/completed and dependencies; teammates self-claim; "Spawning teammates also requires an interactive session. In non-interactive mode with the `-p` flag ... Claude doesn't spawn teammates"; split panes need tmux or iTerm2; hooks `TeammateIdle`, `TaskCreated`, `TaskCompleted` (exit 2 to block/send feedback); plan approval is auto-granted by lead "without the lead reviewing it"; limitations: no resume of in-process teammates, "Task status can lag", one team per session, no nested teams, "Lead is fixed"; "Agent teams use significantly more tokens"; inter-agent messages are marked as from another session and "can't approve a permission prompt" — [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams)
- Agent view: `claude --bg "..."`; states Working / Needs input / Idle / Completed / Failed / Stopped; "Before editing files, Claude moves the session into an isolated git worktree under `.claude/worktrees/`"; "A separate supervisor process runs them"; "background sessions consume your subscription usage the same as interactive sessions, so running ten agents in parallel uses quota roughly ten times as fast"; sessions are local and stop if the machine shuts down — [code.claude.com/docs/en/agent-view](https://code.claude.com/docs/en/agent-view)
- Dynamic workflows: "A dynamic workflow is a JavaScript script that orchestrates many subagents"; "Who decides what runs next ... The script"; can "have independent agents adversarially review each other's findings before they're reported"; `agent()`, `pipeline()`, `parallel()`, `phase()`; up to 16 concurrent agents by default, 1,000 agents/run; stalled agents restart up to 5 times; runs pause at usage limits (v2.1.271+); `Large workflow` warning at >25 agents or >1.5M projected tokens; `/deep-research` bundled; `ultracode` keyword/effort — [code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows)
- Projects: "one ongoing conversation where Claude coordinates a stream of related work"; "Threads: the workers. Each is a separate session with its own context window ... A cloud thread works on its own branch and opens a pull request"; the coordinator "sees what threads report back, not every step they take"; Overview states Ready for review / Waiting on you / Working / Landing / Idle / Resolved; threads auto-fix CI and address review comments; "Project memory ... stored as files. Every cloud thread reads the index file `MEMORY.md` when it starts"; project instructions up to 16,000 characters; "Threads compact automatically, and the conversation works from recent messages, recent threads, and project memory rather than its full history"; thread-count limits given in chat are "instructions Claude keeps to, not enforced settings"; new projects default to Opus high effort for threads — [code.claude.com/docs/en/claude-projects](https://code.claude.com/docs/en/claude-projects)
- Routines (research preview): "a prompt, one or more repositories, and a set of connectors, packaged once and run automatically" on Anthropic-managed or self-hosted cloud; triggers Scheduled (min 1 hour) / API `/fire` with bearer token / GitHub PR & release events; "Routines run autonomously as full Claude Code cloud sessions: there is no permission-mode picker"; "Routines draw down subscription usage the same way interactive sessions do"; 100 scheduled runs/hour/account; a green status "does not mean the task in your prompt succeeded" — [code.claude.com/docs/en/routines](https://code.claude.com/docs/en/routines)
- Channels (research preview): Telegram/Discord/iMessage plugins push messages into a running local session; `/plugin install telegram@claude-plugins-official`, BotFather token, pairing code; sender allowlist — [code.claude.com/docs/en/channels](https://code.claude.com/docs/en/channels); setup walkthrough — [fast.io guide (secondary)](https://fast.io/resources/claude-channels-guide.md)
- Managed Agents (beta header `managed-agents-2026-04-01`): memory stores mount as a directory in the sandbox; "every change creates an immutable memory version"; up to 8 stores/session; docs warn a prompt injection could write malicious content, recommend `read_only` for reference material — [platform.claude.com/docs/en/managed-agents/memory](https://platform.claude.com/docs/en/managed-agents/memory); Oct 7 2026: `web_fetch` restricted to URLs already in session to reduce exfiltration; Jul 22 2026: effort levels + environment/memory-store webhooks — [Claude Platform release notes](https://platform.claude.com/docs/en/release-notes/overview); Managed Agents announced at Code with Claude May 6 2026 — [InfoQ](https://www.infoq.com/news/2026/05/code-with-claude/); scheduled Managed Agents reportedly bill per token plus $0.08/session-hour vs subscription billing for routines — [dev.to (secondary)](https://dev.to/dzhuneyt/routines-vs-managed-agents-where-recurring-claude-work-should-live-cgn)

## KQ1: How do systems represent task state and worker assignment? Is "file-based handoff + marker files" common?

### Takeaway
The dominant representations are (a) an external issue tracker as control plane (Symphony: Linear/GitHub/Jira; Copilot; Paperclip's internal tracker; Gas Town's Beads), (b) a JSON task list with a `passes` flag (Anthropic harness `feature_list.json`, snarktank `prd.json`, ralph-tui), and (c) git branches/PRs as the unit of completion (Projects, Codex, Cursor, Devin). Plain file-based handoff is widespread but almost always *JSON-structured* (Claude agent teams' mailbox and task-list files, beads JSONL/Dolt export, prd.json); free-form request/verdict Markdown files with marker-file state transitions are idiosyncratic to Saga, though the Symphony `WORKFLOW.md` prompt-template and Agent Teams' JSON inboxes are near relatives.

### Cited Findings
- Symphony: tracker is the control plane; no built-in states, operators configure `active_states`/`terminal_states`; "Ticket writes (state transitions, comments, PR links) are typically performed by the coding agent"; scheduler state is in-memory with "tracker/filesystem-driven restart recovery without requiring a persistent database" — [SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)
- Beads: "Distributed graph issue tracker for AI agents, powered by Dolt"; `bd ready` lists "tasks with no open blockers"; `bd update --claim` "Atomically claim a task (sets assignee + in_progress)"; "Hash-based IDs (`bd-a1b2`) prevent merge collisions in multi-agent/multi-branch workflows"; "`.beads/issues.jsonl` is an export for viewers and interchange, not the source of truth or a backup" — [beads README](https://github.com/steveyegge/beads)
- Gas Town: a bead closes only when its PR merges; "hooks" (worktrees) hold each worker's current task; convoys bundle beads — [Wangdhen](https://tenzinwangdhen.com/posts/gastown-good-bad-ugly/); [gastown README](https://github.com/steveyegge/gastown)
- Claude agent teams: shared task list at `~/.claude/tasks/{team-name}/` with pending/in progress/completed and dependencies; mailbox "a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`"; "Task claiming uses file locking"; "Claude Code validates every entry when it reads a mailbox file. Entries that don't match the message format are reported as errors and removed" — [agent-teams docs](https://code.claude.com/docs/en/agent-teams)
- Claude Projects: threads as workers; Overview groups threads by Ready for review / Waiting on you / Working / Landing / Idle / Resolved; "Resolved ... automatically after a week with no activity" — [claude-projects docs](https://code.claude.com/docs/en/claude-projects)
- Anthropic harness: `feature_list.json` where agents may only flip `passes`; JSON chosen because "models are less likely to inappropriately overwrite it than Markdown" — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- snarktank/ralph: `prd.json` user stories with `passes`; "Pick the highest priority story where `passes: false`" — [snarktank/ralph](https://github.com/snarktank/ralph); ralph-tui trackers: "prd.json (simple)" and "Beads (git-backed with dependencies)" — [ralph-tui](https://github.com/subsy/ralph-tui)
- frankbria: `fix_plan.md` checkbox list + `status.json` — [frankbria](https://github.com/frankbria/ralph-claude-code); ralph-orchestrator: "Disk Is State, Git Is Memory" — [ralph-orchestrator](https://mikeyobrien.github.io/ralph-orchestrator/)
- Paperclip: tasks with "comments, plans, blockers, files, and run history"; "A single assignee and execution locks prevent competing runs from claiming the same task"; embedded PostgreSQL — [paperclip README](https://github.com/paperclipai/paperclip)
- Devin: child sessions launched with "prompts, playbooks, tags, and ACU limits"; coordinator notified "when a child finishes or needs input" — [Devin docs](https://docs.devin.ai/work-with-devin/advanced-capabilities)
- Copilot: "one pull request per task", GitHub issue/PR as the task record — [GitHub docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- Magentic-One: Task Ledger + Progress Ledger held by the orchestrator — [Microsoft Research](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- Dynamic workflows: "Where intermediate results live ... Script variables"; a script "holds the loop, the branching, and the intermediate results" — [workflows docs](https://code.claude.com/docs/en/workflows)
- Other file/git-native task boards in the catalogue: gnap "Git-native protocol using a shared repo as a task board" (resting), Concord MCP "coordination protocol for agents to claim work and detect edit collisions", Cyclops "durable mailbox", wit "Locks individual functions via Tree-sitter" — [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)

### Inferences
- Atomic claim semantics (Beads `--claim`, Paperclip execution locks, agent-teams file locking) are the common fix for the duplicate-work failure Gas Town users hit ("Three Mayors ran at once"). Saga's single-decider model sidesteps this only as long as Odin is the sole assigner.
- Everyone who tried Markdown as the machine-readable state record moved to JSON or a database (Anthropic's explicit rationale; Beads' SQLite→Dolt; Vibe Kanban's SQL). Saga's YAML request files to Heimdall are consistent with this; free-text verdict Markdown from Mimir is the outlier.
- Issue-tracker-as-control-plane (Symphony, Copilot, Paperclip) gives humans and agents the same surface; Saga's Telegram + files split means the human has no board view unless Saga builds one.

### Gaps
- No source quantifies how often Beads' Dolt backend corrupts or stalls beyond Yegge's own remark that it is "still a bit janky" under ~12,000 commits/day — [Yegge essay](https://yegge.ai/essays/the-shape-of-things-to-come/).
- I found no system other than Saga that uses marker files (touch-file state transitions) as a first-class protocol; absence of evidence, not a confirmed negative.

## KQ2: Worker isolation, merge/integration, and preventing cross-worker contract drift

### Takeaway
Isolation converged on three substrates: git worktrees on one machine (Claude Squad, Conductor, Vibe Kanban, Superset, Gas Town polecats, agent view, `/batch`), per-task directories/containers on a host (Symphony workspaces, Docker in some managers), and per-session cloud VMs (Devin, Codex, Cursor, Jules, Copilot, Claude Projects threads). Integration is almost universally "one PR/branch per worker" with human merge; only Gas Town (Bors-style bisecting Refinery), Paperclip-like approval stages, and Yegge's Wheelhouse ("Continuous Thunderdome", fix-forward on main) automate the merge. Contract drift is handled mechanically where it is handled at all (OpenAI's linters and structural tests; ralph-orchestrator gates); explicit verbatim interface contracts carried into each worker's PRD, as Saga does, is not documented in any surveyed system.

### Cited Findings
- Claude Squad: tmux session + git worktree per agent — [claude-squad](https://github.com/smtg-ai/claude-squad); Superset: "Worktrees separate working files; they do not sandbox processes or prevent merge conflicts" — [superset](https://github.com/superset-sh/superset); Crystal: worktrees against a single directory — [crystal](https://github.com/stravu/crystal); Vibe Kanban: "each workspace gives an agent a branch, a terminal, and a dev server" — [vibe-kanban](https://github.com/BloopAI/vibe-kanban)
- Claude Code: agent view moves a background session "into an isolated git worktree under `.claude/worktrees/`" before edits; agent teams "don't isolate teammates in worktrees, so partition the work so each teammate owns a different set of files"; `/batch` = 5–30 worktree-isolated subagents — [agents docs](https://code.claude.com/docs/en/agents); [agent-view docs](https://code.claude.com/docs/en/agent-view)
- Symphony: one workspace dir per issue, reused across runs; "Run the coding agent only in the per-issue workspace path"; `codex.thread_sandbox` default `workspace-write`; optional SSH multi-host appendix — [SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md); [elixir README](https://github.com/openai/symphony/blob/main/elixir/README.md)
- Cloud VMs: Devin "each running in its own isolated VM" — [Devin docs](https://docs.devin.ai/work-with-devin/advanced-capabilities); Cursor "isolated VMs in the cloud" — [Cursor docs](https://cursor.com/docs/cloud-agent); Jules "runs in a virtual machine" — [Jules docs](https://jules.google/docs); Copilot "ephemeral cloud development environment" — [GitHub docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent); Projects: "A cloud thread works on its own branch and opens a pull request" — [Projects docs](https://code.claude.com/docs/en/claude-projects)
- Gas Town merge: Refinery "batches merge requests, runs verification gates, and merges to main with a Bors-style bisecting queue. Polecats never push directly to main"; green batches merge, red batches bisect — [gastown README](https://github.com/steveyegge/gastown); Appleton: Refinery may "re-imagine" implementations on messy conflicts — [Appleton](https://maggieappleton.com/gastown)
- Wheelhouse: "Continuous Thunderdome" replaces batched merge-queue CI with commits slammed onto main and fix-forward; "Land Rush" megabatch at queue=100; the merge queue "stalled under load" before this — [Yegge essay](https://yegge.ai/essays/the-shape-of-things-to-come/)
- Projects threads: after opening a PR, "It pushes fixes when CI fails, addresses review comments"; cards offer Resolve conflicts / Fix CI / Address comments / Merge it — [Projects docs](https://code.claude.com/docs/en/claude-projects)
- Agent HQ: "one-click merge conflict resolution", "branch controls for agent-created code" — [github.blog](https://github.blog/news-insights/company-news/welcome-home-agents/)
- Contract drift, mechanical: OpenAI fixed layers "Types → Config → Repo → Service → Runtime → UI" with validated dependency directions, "enforced mechanically via custom linters ... and structural tests", "By enforcing invariants, not micromanaging implementations" — [OpenAI harness post](https://openai.com/index/harness-engineering/); ralph-orchestrator "Gates that reject incomplete work — tests, lint, typecheck must pass" — [ralph-orchestrator](https://mikeyobrien.github.io/ralph-orchestrator/); bernstein runs "lint, type, and test gates before results are merged" — [bernstein](https://pypi.org/project/bernstein/)
- Contract drift, by partition: agent-teams guidance "Break the work so each teammate owns a different set of files" — [agent-teams](https://code.claude.com/docs/en/agent-teams); Devin example prompt asks for "independent work packages" that "won't conflict" — [Devin docs](https://docs.devin.ai/work-with-devin/advanced-capabilities); OpenAI made the app "bootable per git worktree" — [OpenAI](https://openai.com/index/harness-engineering/)
- Spec-first scaffolding: Anthropic's initializer "sets up the environment on the first run" and writes the feature list before any coding session — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); Wheelhouse crew "design work and write Beads implementation plans" before fleet implementation — [Yegge essay](https://yegge.ai/essays/the-shape-of-things-to-come/)
- Catalogue entries on conflict prevention: wit (function-level locks via Tree-sitter), Concord MCP (claim work / detect edit collisions), foremerge ("intent declarations and gated acceptance"), YYLO ("risk-based merge queue"), Aperant ("automatic merge-conflict resolution") — [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)

### Inferences
- Docker-per-worker (Saga) is heavier than the mainstream local choice (worktrees) but matches the cloud vendors' isolation level; the published pain with worktrees (no process sandboxing, sub-agent worktree branch confusion) argues Saga's choice is defensible for unattended runs.
- Saga's "verbatim contract in each PRD" is a prompt-level (cultural) control; the ecosystem's convergent answer to drift is mechanical (linters, structural tests, type checks run as gates). The two are complementary and Saga currently lacks the mechanical half unless dvergar run project linters as gates.
- Automated merge queues are rare and the one well-known implementation (Refinery) stalled under load for its own author; "PR per worker, human merges" remains the safe default.

### Gaps
- No surveyed system documents a "shared scaffold first, then fan out" step as an explicit orchestrator phase apart from Anthropic's initializer; whether Wheelhouse's crew-design stage produces interface files is not described.

## KQ3: Review and audit roles, and how they are triggered

### Takeaway
Review roles are now common and come in four triggers: (1) a stop/idle hook that runs a reviewer before a worker may finish (OpenAI's codex-plugin-cc review gate; Claude `TeammateIdle`/`TaskCompleted` hooks exit 2; ralph-orchestrator gates), (2) an adversarial "refute done" pass by a different model with fresh context (no_human; autoreason's critic + blind judges; dynamic workflows' adversarial verification), (3) role-level reviewers inside the orchestrator (Wheelhouse Fable review stage; kodo's verifier; Dex's multi-reviewer), and (4) human gates at PR merge or plan approval (Jules plan approval, Copilot PR, Projects "Waiting on you", Paperclip approval stages). Cross-model review is an established community pattern between Claude Code and Codex but is usually post-hoc on diffs, not a standing auditor of planner decisions as Mimir is.

### Cited Findings
- OpenAI `codex-plugin-cc` includes an optional review gate that runs a Codex review when Claude Code stops; README warns this can cause long loops — [tarekalaaddin (secondary)](https://www.tarekalaaddin.com/blog/codex-plugin-claude-code-cross-provider-review); [taupe.site](https://taupe.site/en/entry/cross-model-ai-code-review/)
- Claude agent teams hooks: "`TeammateIdle`: runs when a teammate is about to go idle. Exit with code 2 to send feedback and keep the teammate working"; "`TaskCompleted` ... Exit with code 2 to prevent completion and send feedback"; plan approval requests are auto-approved by the lead "without the lead reviewing it" — [agent-teams](https://code.claude.com/docs/en/agent-teams)
- Dynamic workflows: can "have independent agents adversarially review each other's findings before they're reported"; `/deep-research` votes on each claim and filters those that fail cross-checking — [workflows](https://code.claude.com/docs/en/workflows)
- no_human: "A different model, fresh context, read-only tools, told to refute 'done'"; tamper guard before review; merge stays human — [no-human](https://pypi.org/project/no-human)
- autoreason: fresh Critic lists weaknesses; fresh judges, "blind Borda count"; incumbent must win k=2 — [autoreason](https://github.com/NousResearch/autoreason)
- Wheelhouse: each bead "goes through Fable design, Opus implementation, and Fable review" — [Yegge essay](https://yegge.ai/essays/the-shape-of-things-to-come/)
- Gas Town: Witness monitors polecats; Wasteland validators "issue stamps on completed work"; Refinery runs verification gates — [yegge.ai/gastown](https://yegge.ai/gastown); [gastown README](https://github.com/steveyegge/gastown)
- Paperclip: "Review and approval stages can be configured"; hires approved; work paused/reassigned/stopped — [paperclip](https://github.com/paperclipai/paperclip)
- Jules: "You can review and approve [the plan] before any code changes are made" — [Jules](https://jules.google/docs); Copilot: review and request refinements before PR creation; session logs — [GitHub docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent); Cursor artifacts (screenshots, videos, logs) and remote desktop for review — [Cursor](https://cursor.com/docs/cloud-agent)
- Symphony: no built-in review; a workflow-defined handoff state such as `Human Review` — [SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)
- OpenAI harness: agents "reviewing their own work and iterating in a loop until agent reviewers were satisfied"; human review comments become docs/tooling updates — [OpenAI](https://openai.com/index/harness-engineering/)
- Routines: PR-review routine triggered on `pull_request.opened` applies a team checklist and leaves inline comments — [routines](https://code.claude.com/docs/en/routines)
- Magentic-One: orchestrator re-plans on stall; advice to pause for human input before high-risk actions — [Microsoft Research](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- Catalogue: Dex "Human-gated planning and multi-reviewer code review"; kodo "a separate agent verifies each result"; Orbi "separate review before merge"; LongHorizon-Harness "independent auditing and checkpoints"; MartinLoop "verifies output, and rolls back failures" — [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)
- Community cross-model tools: Claude writes / Codex reviews / loop until clean — [atompilot](https://github.com/atompilot/claude-code-cross-review); parallel Codex+Claude review with cross-family verification of each finding — [0-to-1-Labs](https://github.com/0-to-1-Labs/codex-pr-review); read-only Codex second opinion — [shimo4228](https://github.com/shimo4228/codex-review)

### Inferences
- "Different model, fresh context, read-only, told to refute" (no_human, autoreason, 0-to-1-Labs) is the recognizable shape of Mimir; what is unusual in Saga is pointing that reviewer at the *planner's decisions* (decomposition, delegation) rather than at diffs.
- The ecosystem's auditors are triggered by lifecycle events (stop hook, idle hook, PR opened); Saga's request-file trigger is functionally a hook but is initiated by the planner's judgment, which means Odin can skip audit. A hook-based mandatory trigger (e.g. on dvergr launch request or on PRD write) would align with mainstream practice.
- First-party auto-approval of teammate plans (Claude agent teams) shows vendors are currently optimizing for throughput over gating; Saga's stricter gates are a deliberate divergence.

### Gaps
- I could not find a surveyed system with a persistent, long-lived auditor session (as opposed to per-event spawned reviewers); Mimir-as-daemon appears unique, but that may reflect documentation gaps.

## KQ4: Stuck-detection and completion-detection signals

### Takeaway
Completion is signalled by (a) an exact-match marker string (`<promise>COMPLETE</promise>`, `LOOP_COMPLETE`, `EXIT_SIGNAL`), (b) a structured checklist reaching all-pass (`feature_list.json`, `prd.json`, `fix_plan.md`), or (c) a tracker state transition / PR opened. Stuck detection uses inactivity timeouts (Symphony 5-min stall, dynamic workflows' stall window with ≤5 restarts, Gas Town GUPP violation/stalled/zombie), progress-plateau heuristics (frankbria's "3 loops with no progress or 5 loops with same errors"; Magentic-One's stall count > 2 → re-plan; workflows' "two rounds in a row make no progress"), and a hard iteration cap (every Ralph derivative; Symphony `max_turns` 20; Copilot 59-minute sessions). autoreason's "incumbent wins twice" is the one principled convergence criterion.

### Cited Findings
- Official ralph plugin: `--completion-promise` exact string match; `--max-iterations` "(default: unlimited)"; advice "Always use `--max-iterations` as a safety net"; escape-hatch prompt pattern "After 15 iterations, if not complete: Document what's blocking progress" — [ralph-loop plugin](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop); detection bugs — [#3632](https://github.com/anthropics/claude-plugins-official/issues/3632), [#81825](https://github.com/anthropics/claude-code/issues/81825)
- frankbria: circuit breaker "3 loops with no progress or 5 loops with same errors", 30-min cooldown, OPEN → HALF_OPEN → CLOSED; exit "Requires BOTH completion indicators AND explicit EXIT_SIGNAL"; too-many-test-only-loops exit — [frankbria](https://github.com/frankbria/ralph-claude-code)
- ralph-orchestrator: "iterates until it outputs `LOOP_COMPLETE` or hits the iteration limit" — [ralph-orchestrator](https://mikeyobrien.github.io/ralph-orchestrator/); snarktank: `<promise>COMPLETE</promise>` when all stories pass, default 10 iterations — [snarktank/ralph](https://github.com/snarktank/ralph)
- Symphony: "If `elapsed_ms > codex.stall_timeout_ms`, terminate the worker and queue a retry" (5 min); exponential backoff capped at 5 min; `agent.max_turns` 20; completion = issue leaves active states — [SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md)
- Claude workflows: "An agent whose output stops arriving for long enough starts over from the same prompt"; "An agent restarts at most five times"; example prompt "keep fixing ... until the type check passes or two rounds in a row make no progress"; "stop once two rounds in a row find nothing new" — [workflows](https://code.claude.com/docs/en/workflows)
- Claude agent teams: "Task status can lag: teammates sometimes fail to mark tasks as completed"; "The lead can stop early too, deciding the team is finished before all tasks are actually complete" — [agent-teams](https://code.claude.com/docs/en/agent-teams)
- Gas Town: health states "GUPP Violation, Stalled, Zombie, Working, and Idle"; GUPP Violation = hooked work with no progress for an extended period; `mountain` convoys get "autonomous stall detection"; Witness "detects stuck agents, triggers recovery" — [gastown README](https://github.com/steveyegge/gastown); in practice "Agents still needed manual prodding", `gt nudge` via tmux — [Wangdhen](https://tenzinwangdhen.com/posts/gastown-good-bad-ugly/)
- Magentic-One: re-plan when stall count exceeds 2 — [Microsoft Research](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- autoreason: "converge if A wins k=2 times"; halt condition praised as the first edit loop with one — [autoreason](https://github.com/NousResearch/autoreason)
- Anthropic harness: failure "Declaring the project done too early" fixed by the feature list defining full scope; "premature completion of features" fixed by self-verification before flipping `passes` — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Copilot: "maximum execution time of 59 minutes" — [GitHub docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent); Devin: coordinator can "Put child sessions to sleep or terminate them", ACU limits per child — [Devin docs](https://docs.devin.ai/work-with-devin/advanced-capabilities)
- Projects: threads "Resolved ... automatically after a week with no activity"; "Threads guessed or stalled instead of asking" is a documented troubleshooting topic — [Projects docs](https://code.claude.com/docs/en/claude-projects)
- `/loop`: "If an iteration ends without either rescheduling or stopping, Claude Code schedules one fallback wakeup about 20 minutes later and ends the loop when that iteration doesn't reschedule either"; recurring tasks expire after 7 days — [scheduled-tasks](https://code.claude.com/docs/en/scheduled-tasks)
- Model-level failure: Yegge's "just two more things" tic with Opus 4.7 "prevented Opus from ever converging on being ready to do real work" — [Yegge essay](https://yegge.ai/essays/the-shape-of-things-to-come/)
- Huntley's "overbaking": a loop left too long "produces odd emergent behavior" — [HumanLayer](https://www.humanlayer.dev/blog/brief-history-of-ralph)

### Inferences
- "Commit plateau" and "test plateau" (Saga's planned signals) are the same family as frankbria's no-progress counter and workflows' two-rounds-no-change rule; they are mainstream heuristics, just rarely productized.
- Every mature system layers at least two signals (marker + cap, or checklist + timeout). Relying on the plugin's promise tag alone is below the ecosystem bar given the open bugs.
- The failure Yegge hit (model never converging because it keeps improving the harness) is a planner-side failure no worker-side cap catches; Saga's Eir gating (auditor + human on self-modification PRs) is the structural answer.

### Gaps
- No source gives measured false-positive/false-negative rates for any stuck detector.

## KQ5: Memory, journals, lessons stores, and evolving principles

### Takeaway
Three layers recur: (1) an append-only per-run progress log (`claude-progress.txt`, `progress.txt`, Paperclip run history), (2) a curated durable knowledge file the agent is told to update (`AGENTS.md`/`CLAUDE.md` learnings, Projects `MEMORY.md`, Beads `bd remember`, Devin knowledge + playbooks, Managed Agents memory stores), and (3) an issue graph as the "why" record (Beads). Several systems version or gate memory edits (Managed Agents immutable versions; Devin "pending knowledge suggestions" reviewed by humans; Paperclip revisioned config), which is the closest analogue to Saga's approval-gated "principles". Narrative first-person journals per agent are not documented anywhere else.

### Cited Findings
- Anthropic: `claude-progress.txt` log plus git log read at session start; JSON feature list as scope memory — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- snarktank: "Append-only learnings for future iterations" in `progress.txt`; "Ralph updates the relevant `AGENTS.md` files with learnings"; "Memory persists via git history, progress.txt, and prd.json" — [snarktank/ralph](https://github.com/snarktank/ralph); Carson: `progress.txt` = "session memory", AGENTS.md = permanent docs — [Ryan Carson](https://x.com/ryancarson/status/2008548371712135632)
- Huntley: "future loops will not have the reasoning in their context window" so notes must go into the repo; tune by adding "signs" — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- Beads: "`bd remember` stores project facts, and `bd prime` prints workflow context and those memories for later sessions"; "Semantic 'memory decay' summarizes old closed tasks to save context window"; Yegge: Git records what changed, Beads records why — [beads README](https://github.com/steveyegge/beads); [v1.0 post](https://steve-yegge.medium.com/gas-town-from-clown-show-to-v1-0-c239d9a407ec); agent identities are beads so they survive crashes — [Appleton](https://maggieappleton.com/gastown)
- Claude Projects: "Project memory ... stored as files. Every cloud thread reads the index file `MEMORY.md` when it starts and opens the other files when it needs them"; Claude writes them itself ("Auto memory"); separate from repo `CLAUDE.md`; "when you correct a thread, also tell Claude to remember the correction" — [Projects docs](https://code.claude.com/docs/en/claude-projects)
- Managed Agents: memory stores mount as directories; "every change creates an immutable memory version, which provides an audit trail and point-in-time recovery"; prompt-injection warning, `read_only` recommended for reference — [managed-agents/memory](https://platform.claude.com/docs/en/managed-agents/memory)
- Devin: "Turn successful sessions into reusable playbooks"; knowledge dedup and conflict resolution; "Review, view, and dismiss pending knowledge suggestions that Devin generates from sessions" — [Devin docs](https://docs.devin.ai/work-with-devin/advanced-capabilities)
- OpenAI: `docs/` directory "treated as the system of record"; human review comments fed back "into documentation updates or tooling"; background "garbage collection" tasks enforce golden principles — [OpenAI](https://openai.com/index/harness-engineering/)
- ralph-orchestrator: memory = "Persistent learning across sessions"; "Disk Is State, Git Is Memory" — [ralph-orchestrator](https://mikeyobrien.github.io/ralph-orchestrator/); claude-flow: SQLite memory with "12 specialized tables" (secondary) — [claude-flow.ruv.io](https://claude-flow.ruv.io/)
- Paperclip: run history per task; "config changes are revisioned so bad changes can be rolled back"; memory itself is roadmap — [paperclip](https://github.com/paperclipai/paperclip)
- Context rot: compaction "can silently delete governance constraints" — [arXiv Governance Decay](https://arxiv.org/pdf/2606.22528); Projects: "Threads compact automatically ... Put anything that must never be dropped in project memory" — [Projects docs](https://code.claude.com/docs/en/claude-projects)
- Catalogue: hermes-agent "Self-improving harness with cross-session memory and generated skills"; ivy-tendril "self-improving memory"; Ouroboros "durable identity and reviewed self-modification"; Mnemoverse re-ranks recall by outcomes — [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)

### Inferences
- Saga's split (per-agent journals + cross-project lessons store + principles) maps onto the ecosystem's progress-log / knowledge-file / policy layers; the ecosystem's extra move is making the knowledge layer *indexed* (`MEMORY.md` as index, Beads queries, memory decay) so it does not bloat context.
- Gated principle evolution has precedent in Devin's reviewed knowledge suggestions and Managed Agents' versioned stores, so pattern (5)'s approval gate is unusual in open source but mainstream in hosted products.
- The governance-decay finding is a direct argument for keeping Saga's principles in a file re-read at session start rather than in conversation context.

### Gaps
- No surveyed system documents a "lessons across projects" store distinct from per-repo memory; Devin's org-level knowledge is the nearest.

## KQ6: Human-in-the-loop surfaces and proactive updates

## KQ7: Cost control, and subscription versus API billing

### Takeaway
Local tools (agent view, agent teams, routines, `/loop`, Superset "your own subscription", Claude Squad) draw on subscriptions; cloud vendors bill either by inclusion in a plan (Codex in ChatGPT, Jules tiers, Copilot premium requests) or at API rates (Cursor cloud agents, Managed Agents per-token + session-hour). Hard cost controls are rare: Paperclip budgets with pause-at-limit, Devin ACU limits per child, Cursor spend limit, workflows' agent caps and "Large workflow" warning, frankbria's call-rate cap. Yegge's figures (~$87k/month API-equivalent, ~$2,800 out-of-pocket on twelve Max accounts, frequent exhaustion, Codex fallback) are the most concrete evidence that subscription-funded orchestrators run into quota walls, not price walls.

## KQ8: Separating the orchestrator "brain" from the infrastructure substrate; heterogeneous worker harnesses

### Takeaway
The cleanest separations are protocol-based: Symphony (spec + tracker adapters + Codex app-server JSON-RPC; the orchestrator is deliberately dumb and the agent does ticket writes), Gas City (declarative `city.toml` packs over pluggable runtimes tmux/subprocess/exec/ACP/Kubernetes, with a reconcile loop), bernstein (no model in the coordination loop), and Claude dynamic workflows (a script holds the plan; agents are the only model calls). Heterogeneous worker pools are common in open source (Gas Town 11 presets, ralph-orchestrator 8 backends, ralph-tui 7, Paperclip ~10 adapters, Vibe Kanban 10+, Conductor 3, Agent HQ multi-vendor) and absent in the first-party Claude surfaces ("In every approach the workers are Claude sessions") and Symphony (Codex app-server only).

### Cited Findings
- Symphony: orchestrator "does not require first-class tracker write APIs"; adapters compute `dispatchable`; agent launched via `bash -lc` with `codex app-server`; "Coding-agent executable that supports the targeted Codex app-server mode" — [SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md); App Server is "a bidirectional JSON-RPC API" — [OpenAI](https://openai.com/index/unlocking-the-codex-harness/)
- Gas City: "controller/supervisor loop that reconciles desired state to running state"; runtime providers "tmux, subprocess, exec, ACP, Kubernetes, and herdr"; packs and `city.toml` — [gascity](https://github.com/gastownhall/gascity)
- bernstein: "No model in the coordination loop ... replay byte-identically"; one LLM call to decompose; 31–40+ CLI agents — [bernstein](https://pypi.org/project/bernstein/)
- Claude workflows: "A workflow script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer" — [workflows](https://code.claude.com/docs/en/workflows); but all workers are Claude: "To involve a different tool, expose it to Claude as an MCP server" — [agents docs](https://code.claude.com/docs/en/agents)

- Deterministic gatekeepers in the catalogue: Fletch "sandboxes each agent in its own repo clone, gating steps on tests"; agentbox per-agent VMs; scion isolated containers; intentic persistent Docker sandbox per agent — [awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)

### Inferences
- The field's working answer to "extract the brain" is a *spec plus adapters* (Symphony) or *declarative config plus reconcile loop* (Gas City), with the planner reduced to prompts in `WORKFLOW.md`/packs and the substrate a dumb poller. Saga's Odin-as-interactive-session is closer to Gas Town's Mayor than to Symphony's orchestrator; extracting it would mean moving decomposition into a reusable prompt/spec and letting a deterministic daemon (Heimdall-like) own polling, dispatch, stall timeouts, and retries.
- A deterministic non-model coordinator outside the agent trust boundary (Saga's Heimdall) has direct analogues in bernstein and in Yegge's "crons watch, models act", and partial ones in Symphony's trusted-config hooks; it is unusual in the GUI managers but principled.
- Heterogeneous workers are table stakes in open source and the obvious hedge against the single-vendor quota wall Yegge describes; Saga's Claude-only pool is the main place it is narrower than the field.

### Gaps
- No source compares reliability of tmux-send-keys nudging versus protocol-level (app-server/ACP) control; anecdotes (Gas Town nudges, Saga's own baseline.json workaround) suggest send-keys is fragile but there is no measurement.

## KQ9: Where Saga's seven patterns are mainstream versus unusual (synthesis)

### Takeaway
Patterns 1, 4, 7 and the worker-side Ralph loop are mainstream shapes with strong precedents; pattern 3 (pub/sub liveness) and pattern 5 (narrative journals + gated principles) have partial precedents; pattern 2 (free-text request/verdict files and marker files) and pattern 6 (a standing healer agent whose PRs are gated by a cross-model auditor plus human) are idiosyncratic, with the closest neighbours being OpenAI's background "garbage collection" PRs and Devin's reviewed knowledge suggestions.

### Inferences
- Mainstream: single conversational planner over ephemeral workers with persistent identity/task records; worktree-or-VM isolation with PR-per-worker; iteration caps plus a second signal; progress file + knowledge file memory; chat ingress + "needs you" surfacing; subscription-funded local pools with API fallback.
- Unusual but principled: deterministic gatekeeper daemon; cross-model auditor of *planner decisions* rather than diffs; approval-gated principle evolution; MQTT liveness (most peers use file mailboxes or tracker polling).
- Idiosyncratic: free-text request/verdict Markdown and marker-file transitions (peers use JSON with validation and locking); a standing healer agent (peers run healing as scheduled background tasks, e.g. routines or OpenAI's GC jobs, not as a persistent role).
- Extraction decision input: the two systems that did extract the brain (Symphony, Gas City) did so by making the orchestrator *less* intelligent (poller + adapters + declarative packs) and pushing judgment into prompts and the workers; Gas Town, which kept a smart Mayor in an interactive tmux session, is the one that "burned down." That is the strongest ecosystem signal for the operator's question.

### Gaps
- No independent benchmark compares any two orchestrators on task-completion reliability; Dan Luu's and Yegge's remarks are the only candid reliability statements found, and both are negative about ultra-vibed orchestrators.
- Whether MQTT-style pub/sub measurably improves stuck detection over file polling is unstudied in the sources found.
