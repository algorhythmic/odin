## Q1. What does "building a custom harness" mean in 2026? Schools of thought, canonical essays, and what each says a harness must contain

### Takeaway
By late 2026 "harness" has a reasonably stable meaning: the software around the model that runs the loop, owns the tool registry, assembles context, persists sessions, gates actions, and exposes a human surface. The schools differ on *how much* belongs in the harness: Anthropic and OpenAI argue for rich, structured harnesses (initializer agents, progress files, repo-local docs, linters, compaction, subagents); Zechner/Pi and Thorsten Ball argue the model is now RL-trained to be a coding agent so the harness should be four tools and a short prompt, with everything else as user-owned extensions or plain files; Hashimoto and the OpenAI "harness engineering" post define the discipline as "every time the agent makes a mistake, engineer it so it never recurs." Karpathy's LLM-wiki and Anthropic's context-engineering post both treat the file system as the durable memory layer, which is the piece most relevant to Odin's journals.

### Cited Findings

**Anthropic, "Effective harnesses for long-running agents" (official, Nov 26, 2025)**
- Core problem: "each new session begins with no memory of what came before"; "compaction isn't sufficient." Even Opus 4.5 in a loop on the Claude Agent SDK could not build a production-quality web app from a high-level prompt without a harness. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Observed failure modes: agent tries too much at once and runs out of context mid-feature; later sessions declare the project finished too early; features marked complete without end-to-end testing. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Harness components: (1) an **initializer agent** that runs once and creates `init.sh`, a progress log (`claude-progress.txt`), and an initial git commit; (2) a **feature list as JSON** (all initially failing) chosen because the model is "less likely to inappropriately change or overwrite JSON files compared to Markdown files" — the coding agent may only flip `passes`; (3) a **coding agent** that works "only one feature at a time," leaves code clean, commits with descriptive messages, updates the progress file; (4) **git history + progress file** as the recovery mechanism; (5) **browser-level testing** (Puppeteer MCP) because unit tests and curl were insufficient; (6) a fixed **startup routine** (pwd, read progress file, git log, feature list, start dev server, smoke test). — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Minimal design: two agents that "differ only in their initial user prompts"; same system prompt, tools, harness. Example produced >200 features. Open question stated by Anthropic: whether one general agent beats a multi-agent split with specialized testing/QA/cleanup agents. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Anthropic, "Building agents with the Claude Agent SDK" (official, Sept 29, 2025)**
- Renamed Claude Code SDK to Claude Agent SDK; the pitch is "the agent harness that powers Claude Code" reused for non-coding agents. Loop: "gather context -> take action -> verify work -> repeat." Design principle: "give your agents a computer, allowing them to work like humans do." — [claude.com blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Harness contents per the post: tools (designed for context efficiency), file system as on-demand context, agentic search (grep/tail) before semantic search, compaction ("automatically summarizes earlier messages as the context limit nears"), subagents with "their own isolated context windows," bash + code generation, MCP for integrations, and verification via linting / screenshots (Playwright) / LLM-as-judge: "Agents that can check and improve their own output are fundamentally more reliable." — [claude.com blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Current SDK capability list (official docs, 2026-10-13): built-in tools, hooks, subagents, MCP, permissions, sessions (resume/fork), skills/commands/memory loaded from `.claude/` and `~/.claude/`, plugins. It "runs the Claude Code binary" as a library in Python/TypeScript; other languages are told to "run the CLI as a subprocess with the `-p` flag and `--output-format json`." — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Anthropic also now sells a hosted harness, **Claude Managed Agents**: "A hosted agent harness that runs the agent loop, with sessions in an Anthropic-managed cloud sandbox or a self-hosted sandbox." — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- The SDK docs link an Anthropic post titled "A harness for every task: dynamic workflows in Claude Code" (how the Claude Code team orchestrates many subagents). — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) (post itself not fetched; see Gaps)

**Anthropic, "Effective context engineering for AI agents" (official, Sept 29, 2025)**
- Defines context engineering as "the art and science of curating what will go into the limited context window," superseding prompt engineering; context has "diminishing marginal returns." Practices: system prompt at the "right altitude" (start minimal, add instructions from observed failures); self-contained, token-efficient tools ("bloated tool sets" are a named failure mode); just-in-time retrieval via lightweight identifiers (file paths); compaction tuned for recall first; **structured note-taking** to persistent files (e.g. `NOTES.md`) outside the window; sub-agents in clean windows returning condensed summaries. Technique selection: compaction for long back-and-forth, note-taking for milestone work, multi-agent for parallel research. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**OpenAI, "Harness engineering: leveraging Codex in an agent-first world" (official, Feb 11, 2026; openai.com returns 403 to fetchers, content read via r.jina.ai proxy and cross-checked with a secondary summary)**
- Setup: internal beta product built with "roughly 0 lines of manually written code"; ~1M lines of code; ~1,500 merged PRs; 3.5 PRs/engineer/day; five months from first commit (late Aug 2025); team of 3 growing to 7; single Codex runs of >6 hours; estimated build time ~1/10 of hand-coding. — [OpenAI via r.jina.ai](https://r.jina.ai/https://openai.com/index/harness-engineering/); author Ryan Lopopolo per [search result summary](https://openai.com/index/harness-engineering/)
- Harness components: **agent-first repo** ("From the agent's point of view, anything it can't access in-context while running effectively doesn't exist"; "Repository-local, versioned artifacts ... are all it can see"); **AGENTS.md as a map** of ~100 lines ("give Codex a map, not a 1,000-page instruction manual"), abandoned the single large instruction file because it crowded context and went stale; **docs/ as system of record** (design docs, architecture maps, quality grades, versioned execution plans with progress and decision logs) with CI checks and a recurring "doc-gardening" agent; **custom linters and structural tests** with remediation text in error messages ("By enforcing invariants, not micromanaging implementations"); **observability per worktree** (ephemeral logs/metrics/traces stack queryable by the agent via LogQL/PromQL, UI driven via Chrome DevTools Protocol); **golden principles + garbage collection** (background Codex tasks scan for drift, update quality grades, open small refactoring PRs, many automerged; previously the team spent every Friday, ~20% of the week, cleaning "AI slop"); **merge philosophy** of minimal blocking gates and short-lived PRs because "corrections are cheap and waiting is expensive." Slogan: "Humans steer. Agents execute." — [OpenAI via r.jina.ai](https://r.jina.ai/https://openai.com/index/harness-engineering/); corroborated by [rohitraj.tech summary](https://rohitraj.tech/en/notes/what-is-harness-engineering-codex-2026)
- Community critique (HN thread on a related "harness engineering" explainer, 128 points): one commenter argues most harnesses "accelerate context pollution and codebase drift through the instructions they embed in system prompts, tool descriptions, and skills"; others complain about proliferating markdown files (HARNESS.md alongside AGENTS.md/CLAUDE.md) and marketing-driven naming. Commenters attribute the term's origin to Hashimoto's post, picked up by OpenAI "about a week later." — [HN mirror](https://hn.nuxt.dev/item/49464970)

**OpenAI, "Unlocking the Codex harness" (official, date not shown on page; read via r.jina.ai)**
- OpenAI's own definition of its harness: "Codex core is both a library where all the agent code lives and a runtime"; components are the core agent loop, thread lifecycle/persistence (create/resume/fork/archive with saved event history), config and auth ("Sign in with ChatGPT"), tool execution in a sandbox, MCP servers and skills "under a shared policy model," approvals (server asks the client and pauses the turn), auto-compaction. "Codex Web uses the Codex harness, but runs it in a container environment." — [OpenAI via r.jina.ai](https://r.jina.ai/https://openai.com/index/unlocking-the-codex-harness)

**Mitchell Hashimoto, "My AI Adoption Journey" (primary, Feb 5, 2026)**
- Six steps: Drop the Chatbot; Reproduce Your Own Work; End-of-Day Agents; Outsource the Slam Dunks; **Engineer the Harness**; Always Have an Agent Running. He writes he has "grown to calling this 'harness engineering'" and defines it: "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again." His harness = AGENTS.md where "each line addresses a specific bad agent behavior," custom scripts/tools (screenshots, filtered tests) paired with AGENTS.md entries, and verification loops ("fast, high quality tools to automatically tell it when it is wrong"). He runs one agent ~10–20% of the day and does not want multiple agents yet. — [mitchellh.com](https://mitchellh.com/writing/my-ai-adoption-journey)

**Mario Zechner / Pi, "What I learned building an opinionated and minimal coding agent" (primary, Nov 30, 2025)**
- Motivation: "inspect every aspect of my interactions with the model"; existing harnesses are "injecting stuff behind your back that isn't even surfaced in the UI"; frontier models are RL-trained to code so "There does not appear to be a need for 10,000 tokens of system prompt." — [mariozechner.at](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)
- Harness: four default tools (`read`, `write`, `edit`, `bash`; read-only `grep`/`find`/`ls` available but off); system prompt + tool defs under 1,000 tokens, only AGENTS.md (global + project) added, fully replaceable; sessions with continue/resume/branching; slash commands as markdown templates; headless JSON/RPC modes. Monorepo: `pi-ai` (unified multi-provider LLM API with streaming, tool calls, cross-provider context handoff, cost tracking), `pi-agent-core` (loop that "loops until the model stops calling tools, with no max-steps setting"), `pi-tui`, `pi-coding-agent`. — [mariozechner.at](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)
- Deliberately removed: MCP ("pi does not and will not support MCP" — prefers CLI tools with READMEs read on demand); dedicated sub-agent tool (sub-agents are "a black box within a black box"; parallel sub-agents "an anti-pattern in my book"; the agent can run itself via bash); plan mode (use PLAN.md); built-in to-dos (TODO.md); background bash (use tmux: "Bash is all you need"); permission checks (runs in YOLO mode; guardrails are mostly "security theater"). Terminal-Bench 2.0 run with Opus 4.5, 5 trials/task; also cites Terminus 2 (tmux keystroke agent) as evidence minimal harnesses compete; benchmarks "aren't representative of real-world performance." — [mariozechner.at](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)
- Community: Earendil acquired Pi from Zechner on April 8, 2026 and launched a cloud platform "Lefos"; Zechner became a stakeholder. — [implicator.ai](https://www.implicator.ai/pi-is-not-a-claude-code-rival-it-is-a-harness-rebellion/) (community). Earendil's "What is a Harness?" post (118 HN points) frames "Agent = Model + Harness" with four components: system prompt, tools, agentic loop, model translation layer; the harness is "software you own and can modify, unlike the model." — [Gigazine summary, Aug 25, 2026](https://gigazine.net/gsc_news/en/20260825-what-is-harness/) (community, secondhand)

**Thorsten Ball, "How to Build an Agent" (primary, Apr 15, 2025)**

### Inferences
- Across all schools, the irreducible harness is: a loop; a small tool set (read/write/edit/bash at minimum); context assembly (system prompt + instruction file + on-demand file reads); durable state outside the window (progress file / JSON feature list / NOTES.md / wiki); verification tooling; and some human surface. Everything else (MCP, subagents, plan mode, permissions, compaction) is contested and can live outside the core as extensions or plain files.
- The Anthropic long-running-agents harness is structurally almost identical to what Saga already does with journals + ralph-loop (progress file, one-feature-at-a-time, git commits, startup routine). The JSON-over-Markdown finding for the feature list is directly transferable to Odin's guidance/feature-tracking files.
- Odin's 1,000-line persona prompt runs against the Zechner/Anthropic-context-engineering consensus (short prompt at the "right altitude," details loaded just-in-time). Extracting Odin into a custom harness is an opportunity to move most of that prompt into skills (progressive disclosure) and repo-local docs (OpenAI's "map, not manual").
- Karpathy's wiki (index.md + log.md + lint) is a ready-made structure for Bragi's vault and Odin's master journal/principles.

## Q2. Reference custom harnesses to study: how each structures tool registry, prompt assembly, compaction, session store, hooks/extensions, sub-agents, sandbox

### Takeaway
There are now three distinct reference shapes: (a) vendor harnesses exposed as libraries/servers (Claude Agent SDK, Codex core + App Server, OpenCode server/SDK) that give you the vendor's loop, compaction, permissions and sessions but tie you to their auth rules; (b) minimal open harnesses (Pi, smolagents, Ball's 400-liner) that give you a loop plus 3–4 tools and push everything else to extensions; (c) "life-agent" harnesses (Hermes, OpenClaw, nanobot) that bundle gateway + cron + skills + memory. For Odin, (a) is the lowest-risk path if billing works (see Q4/Q5), (b) is what "custom harness developed in parallel" literally means, and (c) is the closest existing shape to Odin + Ratatoskr (Telegram gateway, scheduled checks, journals).

### Cited Findings

### Inferences
- The shape that matches Odin most closely is "Hermes/OpenClaw-class harness minus the kitchen sink": a loop + gateway (Telegram) + scheduler + skills + file-backed memory. Pi's package split (`pi-ai` provider layer, `pi-agent-core` loop, `pi-durable` state, `chord` plugin host) is the cleanest decomposition to copy if the operator writes their own.
- If Odin becomes a custom harness, the worker side can stay on whatever harness each dvergr uses, provided the orchestrator speaks ACP (Q3) or each vendor's headless JSON stream.
- Hermes' documented "Max + extra-usage-credits only" Anthropic path and the user-reported failures are a concrete warning: third-party harnesses hitting `api.anthropic.com` with subscription OAuth are exactly what Anthropic's policy forbids (Q6), so a custom Odin should plan on API-key auth funded by the new Max API credits (Q5) rather than OAuth tricks.

## Q3. Interop protocols: ACP, MCP, A2A, AG-UI, Agent Skills, AGENTS.md, OTel GenAI — which let an orchestrator drive Claude Code, Codex, and Gemini uniformly?

### Takeaway
ACP is the only protocol that standardizes *driving a coding-agent session* (prompt in, streamed updates out, permission callbacks, fs/terminal delegation) and it has adapters for Claude (via Agent SDK), Codex (via App Server), OpenCode, Goose, Kiro, Hermes, Pi, Cursor, Copilot CLI and ~35 others; headless clients and orchestrators exist. MCP (now at revision 2026-07-28) is for tools, not agents, and has moved sharply toward stateless request/response with sampling/roots deprecated. A2A is for agent-to-agent delegation across organizations (JSON-RPC/gRPC/HTTP, Linux Foundation), AG-UI is the UI event stream, Agent Skills + AGENTS.md normalize the instruction layer, and OTel GenAI normalizes telemetry. The practical catch for Google: Gemini CLI (which had native `--acp`) stopped serving free/AI Pro/AI Ultra accounts on June 18, 2026; its successor Antigravity CLI has no ACP support per community reports, so "Gemini over ACP with a Google account" is currently not a working path.

### Cited Findings

**Agent Client Protocol (ACP)**
- Model: JSON-RPC 2.0; Agents "typically run as subprocesses of the Client"; Clients are "typically code editors ... though other UIs can also act as Clients." Methods: `initialize`, `authenticate`, `session/new`, `session/load`, `session/prompt` (agent streams `session/update` notifications, ends with a stop reason), `session/cancel`; Client-side `session/request_permission`, optional `fs/read_text_file`, `fs/write_text_file`, and `terminal/create|output|release|wait_for_exit|kill` gated by capabilities. — [ACP protocol overview](https://agentclientprotocol.com/protocol/overview)
- Local agents "communicate via JSON-RPC over stdio"; remote agents over HTTP/WebSocket but "Full support for remote agents is a work in progress." — [ACP introduction](https://agentclientprotocol.com/overview/introduction)
- Protocol version is integer `1`; bumps only on breaking changes; features via capabilities (`fs.readTextFile/writeTextFile`, `terminal`, `loadSession`, `promptCapabilities.image/audio/embeddedContext`, `mcpCapabilities.http/sse`); "Clients and Agents MUST treat all capabilities omitted in the initialize request as UNSUPPORTED." — [ACP initialization](https://agentclientprotocol.com/protocol/initialization)
- Registry lists 43 agents including: Claude Agent "via Zed's SDK adapter (claude-agent-acp)," Codex CLI "via the ACP adapter (codex-acp)," Gemini CLI, OpenCode, Goose, Kiro CLI, Hermes Agent, Pi (pi-acp), Cursor, GitHub Copilot CLI (public preview), OpenHands, OpenClaw, Cline, Kimi CLI, Qwen Code, Mistral Vibe, Factory Droid, Augment, JetBrains Junie, Docker cagent, fast-agent. — [ACP agents](https://agentclientprotocol.com/overview/agents)

- Governance: "jointly governed by JetBrains and Zed"; coordination via Zulip, GitHub Issues, RFD process (from a JetBrains job posting). - Gemini CLI: Zed "runs Gemini CLI in the background, and talks to it over ACP"; Goose's Gemini ACP provider uses "Google's Gemini CLI directly via its native --acp flag." — [Zed external agents](https://zed.dev/docs/ai/external-agents); [Goose ACP providers](https://goose-docs.ai/docs/guides/acp-providers)

**Model Context Protocol (MCP), latest revision 2026-07-28 (official changelog)**
- Major changes since 2025-11-25: protocol-level sessions and `Mcp-Session-Id` removed; the `initialize` handshake removed (version + capabilities travel in `_meta` on every request); new `server/discover`; `subscriptions/listen` single long-lived stream replaces GET endpoint and resource subscribe/unsubscribe; `ping`, `logging/setLevel`, roots-changed notifications removed; **tasks moved out of core into an official extension** (`io.modelcontextprotocol/tasks`, polling `tasks/get`, `tasks/update`); **Multi Round-Trip Requests (MRTR)** replace server-initiated `sampling/createMessage`, `elicitation/create`, `roots/list` — servers return `resultType: "input_required"` and the client retries with `inputResponses`; SSE resumability removed. Minor: `extensions` capability field; **OpenTelemetry trace context propagation in `_meta` (`traceparent`, `tracestate`, `baggage`)**; deterministic `tools/list` ordering "to improve LLM prompt cache hit rates"; `ttlMs`/`cacheScope` on list results. **Deprecated: Roots, Sampling, and Logging** ("integrate directly with LLM provider APIs instead of Sampling; log to stderr or use OpenTelemetry instead of Logging"); HTTP+SSE transport; Dynamic Client Registration in favor of Client ID Metadata Documents. 12-month minimum deprecation window adopted. — [MCP changelog](https://modelcontextprotocol.io/specification/latest/changelog)

**A2A (Agent2Agent)**
- "originally developed by Google and donated to the Linux Foundation"; Technical Steering Committee with AWS, Cisco, Google, IBM Research, Microsoft, Salesforce, SAP, ServiceNow; Apache 2.0; banner says A2A is joining the Agentic AI Foundation; site links "What's New in v1.0." "The Model Context Protocol (MCP) and the A2A Protocol are not competitors": MCP = agent-to-tool, A2A = agent-to-agent (discover, delegate, share results); A2A "does not specify how an agent manages its own sub-agents or invokes tools." — [a2a-protocol.org](https://a2a-protocol.org/latest/)

**AG-UI**
- "an open, lightweight, event-based protocol that standardizes how AI agents connect to user-facing applications"; "born from CopilotKit's initial partnership with LangChain and CrewAI"; builds on HTTP/WebSockets; "streamed event-sourced diffs" for shared state; integrations: LangChain, CrewAI, Microsoft Agent Framework, Google ADK, AWS Strands/AgentCore, Mastra, Pydantic AI, Agno, LlamaIndex; community integrations for Claude Agent SDK and Claude Managed Agents SDK; a client "does not have to be a web application." Positions itself as the third layer with MCP (tools) and A2A (agents). — [docs.ag-ui.com](https://docs.ag-ui.com/introduction)

**Agent Skills (agentskills.io)**
- A skill is a folder with `SKILL.md` (name + description + instructions) plus optional `scripts/`, `references/`, `assets/`; loaded by **progressive disclosure** (discovery: name/description only; activation: full SKILL.md; execution: bundled files). "originally developed by Anthropic, released as an open standard." Client list includes Claude Code, Claude, ChatGPT & Codex, Gemini CLI, OpenCode, Goose, Cursor, GitHub Copilot, VS Code, Kiro, Hermes Agent, OpenClaw, Pi, Factory, Amp, Letta, OpenHands, Roo Code, Mistral Vibe, JetBrains Junie, nanobot, fast-agent, Databricks, Snowflake, Spring AI. — [agentskills.io](https://agentskills.io/)

**AGENTS.md**
- "a README for agents"; emerged from OpenAI Codex, Amp, Jules, Cursor, Factory; "now stewarded by the Agentic AI Foundation under the Linux Foundation"; "used by over 60k open-source projects"; plain Markdown, no required fields; nested files allowed, "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything"; supported by Codex, Jules, Gemini CLI (via `context.fileName`), Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, Windsurf, Junie, Amp, Cursor, RooCode, Copilot coding agent, Ona, Augment. CLAUDE.md not mentioned. — [agents.md](https://agents.md/)

**OpenTelemetry GenAI semantic conventions**
- Moved out of the main semconv repo to `open-telemetry/semantic-conventions-genai` (Apache-2.0); covers "spans, metrics, and events for GenAI clients," plus MCP and provider-specific (OpenAI) conventions; `docs/gen-ai/` holds "GenAI client inference, agents, tool execution, evaluation, and MCP"; `docs/registry/` holds `gen_ai.*`, `mcp.*`, `openai.*` attribute namespaces. Stability status and version not stated on the pages fetched ("Schema URL: TODO"). — [opentelemetry.io notice](https://opentelemetry.io/docs/specs/semconv/gen-ai/); [GitHub repo](https://github.com/open-telemetry/semantic-conventions-genai); [docs folder](https://github.com/open-telemetry/semantic-conventions-genai/tree/main/docs)
- MCP 2026-07-28 formally documents OTel trace-context propagation in `_meta`. — [MCP changelog](https://modelcontextprotocol.io/specification/latest/changelog)

### Inferences
- To treat Claude, Codex, and (an open-weight or OpenCode) worker uniformly today, ACP is the only standard "driver" protocol; a headless ACP client (acp-cli/acpx, or a Python client via ACP Kit / fast-agent) can replace Ratatoskr's tmux send-keys with a real request/response channel that includes permission callbacks and streamed tool-call events. Gemini is the exception until Antigravity CLI gains ACP; for Google the fallback is the Gemini API directly or `agy -p` (community reports it hangs without a TTY).
- ACP's capability negotiation (client-provided `fs` and `terminal`) maps naturally onto Heimdall: the orchestrator-as-Client can refuse terminal capability and force the agent to request permission for every tool call, giving the gatekeeper a protocol-level hook instead of container-only isolation.
- MCP's direction (stateless, sampling deprecated, OTel in `_meta`) means MCP should be used for Saga's tools (MQTT publish, journal read/write) but not for agent-to-agent control; A2A is overkill for a single-operator homelab but its Task/Artifact vocabulary is a reasonable model for the dvergr journal schema.
- Agent Skills + AGENTS.md are the portable instruction layer: moving Odin's persona content into skills and a short AGENTS.md makes it loadable by any of the listed harnesses, which is the precondition for "Saga hosts workers from other harnesses."
- OTel GenAI (`gen_ai.*` spans/metrics) is the right wire format for the MQTT event bus to become harness-agnostic telemetry; Grafana/InfluxDB at .15 can consume it.

- Antigravity CLI's official ACP status is unconfirmed; only a community forum complaint and absence of mention in Google's post.

## Q6. Provider policies on unattended/automated use and third-party harnesses (Anthropic, OpenAI, Google), as of October 2026

### Takeaway
Anthropic is the strictest on paper and in enforcement: consumer OAuth is for Claude Code and native Anthropic apps, third-party harnesses may not route through Pro/Max credentials, and "advertised usage limits ... assume ordinary, individual usage" — yet Anthropic also states that `claude -p`, the Agent SDK, and third-party apps still draw on subscription limits, and it has blocked specific harnesses (OpenClaw) rather than publishing a general automation ban. OpenAI's terms contain generic anti-automation language, but its Codex docs ship headless modes on plan auth, its Codex lead endorses third-party harness use, and it sells automation access tokens for workspaces. Google has retired the consumer-plan CLI entirely; the only Google path with published terms for automation is a paid API key.

### Cited Findings
- **Anthropic (official):** see Q4 for verbatim text from [code.claude.com legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance): OAuth "designed to support ordinary use of Claude Code and other native Anthropic applications"; Agent SDK developers "should use API key authentication"; no third-party claude.ai login or routing through consumer credentials; "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice"; hosting the unmodified Claude Code binary in "hosted sandboxes or other agent infrastructure" is permitted under Commercial Terms if each end user authenticates with their own credentials and the binary's auth methods are untouched. ### Inferences
- Saga's current design (unmodified Claude Code binaries in containers, each authenticating with the operator's own subscription via Anthropic's own `/login` flow) is inside the letter of Anthropic's hosting clause.
