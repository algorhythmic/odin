**Identity check:** The URL resolves to the intended project. It is not exo-explore/exo, the distributed-inference project. The repo moved from `ankrgyl/exo` to `exoharness/exo` on 2026-07-09 ([PR #128](https://github.com/exoharness/exo/pull/128)). Between late September and October 2026 the project was repositioned. ## 2. Architecture: loop, tools, prompt assembly, context and compaction, memory, persistence, multi-agent, scheduling, gateways, observability, storage

### Takeaway
Exo separates a trusted durable substrate (the "exoharness": event log, artifacts, vaults, sandboxes) from a swappable harness that owns prompts, model calls, tools, and compaction. The bundled `claude-code` harness drives Claude Code through the Claude Agent SDK, one fresh process per turn, replaying Exo's history as a transcript. The basic loop replays the full history every round and has no conversation compaction. Memory, scheduler, and chat adapters exist only in the archived self-agent; in the current product they are marked "planned".

### Cited Findings
**Layering and data model**
- "The exoharness… owns identity (agents, threads, turns), history (the append-only event log), artifacts, vaults, and sandbox management. It stores and orders events, but doesn't decide which events to put in the prompt or when to call the model." The harness "assembles prompts, calls models, dispatches tools, and decides how to manage context." — [harnesses.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/harnesses.md)
- Hierarchy: Agent → Thread → Sessions → Turns, plus a per-thread Sandbox. "Exo durably queues submitted turns and serializes execution within a thread." `begin_turn(...)` returns a turn handle. — [data-model.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/data-model.md)
- Events use UUIDv7 IDs and are exposed through `get_events`, `get_event`, and `watch_events`. Custom event types should be namespaced. "Compaction never needs to be a first-class exoharness concept": a harness writes a custom event pointing at a summary. — [data-model.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/data-model.md)
- Core event kinds: thread_created/updated/deleted/forked, session_started/ended, turn_started/ended, messages, tool_requested, tool_result, lingua_stream_chunk, error, artifact_written, sandbox_created/started/stopped/attached/detached/snapshotted, sandbox_process_started/state_updated/event, and Custom. — [crates/exoharness/src/types.rs](https://github.com/exoharness/exo/blob/main/crates/exoharness/src/types.rs) (the `EventData::kind` mapping)
- Artifacts are "opaque, immutable, versioned" blobs written through the event log. — [data-model.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/data-model.md)

**Agent loop (basic "responses" loop used by custom TS harnesses and the archived agent)**
- Each round rebuilds the tool registry and calls `materializePromptMessages`, which is instructions plus *all* conversation messages and tool events. It then calls the model with streaming (`completeStream`, emitting text deltas and time to first chunk) or without. It appends the events, then executes tool calls one by one in a `for` loop. It stops when there are no tool calls or when `maxToolRoundTrips` is exceeded. — [turn-loop.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/model-runtime/turn-loop.ts); [harness/index.ts `materializePromptMessages`](https://github.com/exoharness/exo/blob/main/exoharness/typescript/harness/index.ts)
- Supported wire APIs in the basic runtime: OpenAI Responses, Chat Completions (used for OpenRouter), and Anthropic Messages streaming. The default Anthropic `max_tokens` is 4096. — [responses.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/model-runtime/responses.ts)
- "Tool definitions are registered fresh each model round, so tools the agent installs mid-turn are visible in the very next round." — [archive canonical-agent.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/canonical-agent.md)

**Claude Code harness (the one most relevant to Saga)**
- It imports `query` from `@anthropic-ai/claude-agent-sdk`. Options: `persistSession: false`, `includePartialMessages: true`, `strictMcpConfig: true`, a `PreToolUse` hook that calls `context.authorizeTool`, and `spawnClaudeCodeProcess` that runs the `claude` binary *inside the Exo sandbox*. Each turn renders the Exo history to a transcript string (`messagesToTranscript`, formatted as "ROLE:\ncontent") and sends it as a single user message. The agent's instructions become `systemPrompt`. — [claude-code-harness.ts](https://github.com/exoharness/exo/blob/main/exoharness/examples/typescript/claude-code-harness.ts)
- Retry and timeout behaviour: the harness aborts after 2 SDK API retries (`CLAUDE_MAX_API_RETRIES = 2`, "aborting instead of waiting for the full SDK retry backoff") and has a 60 s startup timeout. — [claude-code-harness.ts](https://github.com/exoharness/exo/blob/main/exoharness/examples/typescript/claude-code-harness.ts)
- Only `ANTHROPIC_BASE_URL`, `CLAUDE_CONFIG_DIR`, `TRACEPARENT`, and `TRACESTATE` are forwarded into the sandboxed process env. HOME is `/home/exo`. — [claude-code-harness.ts](https://github.com/exoharness/exo/blob/main/exoharness/examples/typescript/claude-code-harness.ts)
- The sandbox image installs `@anthropic-ai/claude-agent-sdk@0.2.126` plus its native Linux binary, symlinked to `/usr/local/bin/claude-code`. — [Dockerfile](https://github.com/exoharness/exo/blob/main/exoharness/containers/claude-code-sandbox/Dockerfile); [version](https://github.com/exoharness/exo/blob/main/exoharness/containers/claude-code-sandbox/version)
- Exo runtime and client tools are exposed to Claude Code through an in-process SDK MCP server named `exo_runtime`. — [claude-runtime-tools.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/harness/claude-runtime-tools.ts)
- A contributor noted on 2026-09-14 that "`--harness claude-code` registers no exo tools at all — no `manage_tool`, no `rebuild_and_restart_exo`". The PR to bridge them (#194) is open and conflicted. — [PR #194](https://github.com/exoharness/exo/pull/194)
- Recovery: "Claude Code and Pi currently end an interrupted turn as failed". Codex reconnects or resumes. — [harnesses.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/harnesses.md)

**Context management and compaction**
- The basic executor has no conversation compaction. The archived self-control doc says "Conversation history is replayed in full each turn". — [docs/SELF-CONTROL.md](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md)
- An open PR, unmerged since 2026-07-26, says: "The basic executor replays the entire event log into every model call. Past the model's input limit… the turn fails, and every subsequent turn fails the same way, permanently." It proposes checkpoint events pointing at summary artifacts, cut only at `turn_ended` boundaries. — [PR #170](https://github.com/exoharness/exo/pull/170)
- Tool results larger than an inline limit are written as artifacts (`result.json`, `stdout.txt`, `stderr.txt`) and the model gets a preview with `truncated: true`. — [harness/tools.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/harness/tools.ts)
- The Codex harness uses Codex's native `thread/compact/start` when replaying long history. — [codex/replay.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/codex/replay.ts)

**Memory**
- The current product lists "Memory store" and "Skills in agent definitions" as unchecked planned additions. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- The archived agent has `remember(text)` and `forget(id)`, stored in one JSON artifact `memory/exo-memory.json` on the agent and capped (oldest entries dropped). The whole store is injected as a developer message every turn. It is "deliberately not embedding-based retrieval". It also has a local profile file `.exo/exo-profile.md`, a `todowrite` todo list shown back every turn, and skills. — [docs/SELF-CONTROL.md](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md); [exo/harness.ts](https://github.com/exoharness/exo/blob/main/exo/harness.ts)

**Persistence, resume, forking**
- Threads resume by slug or ID (`exo run AGENT --thread THREAD`). Forks are made with `exo thread fork … --up-to EVENT_ID`. Clients disconnect and reconnect through `/event/watch?after=EVENT_ID`. "The turn keeps running on the server." — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Local state lives under `~/.exo` (`--root` or `EXO_HOME`). The file encryption key is at `<root>/exoharness/master.key`. — [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md). Storage dependencies include sqlx (sqlite and postgres) and object_store (fs, aws, gcp, azure). — [Cargo.toml](https://github.com/exoharness/exo/blob/main/Cargo.toml)
- A Cloudflare Workers runtime was merged 2026-10-05 ("Run managed agents on Cloudflare Workers"). — [PR #369](https://github.com/exoharness/exo/pull/369); [exoharness/cloudflare](https://github.com/exoharness/exo/tree/main/exoharness/cloudflare)

**Sub-agents and multi-agent**
- The only mention of sub-agents is that a turn "may map to many LLM calls (tool loops, subagents)". — [data-model.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/data-model.md); [spec.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/spec.md). An HTTP server can host multiple agents and threads (`/exo/agent/{id}/thread/{id}`). — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)

**Scheduling**
- The archived scheduler has these tools: `schedule_sandbox_task`, `list_scheduled_tasks`, `cancel_scheduled_task`, `delete_scheduled_task`. Schedule forms are `@every`, simple cron, and `@at <rfc3339>` one-shots. Fires land on an anchored grid. A `missed` policy chooses skip, once (default), or all (capped at 100). Each run wakes the conversation with a turn based on `reportPrompt`. Delivery is at-least-once, keyed by (task, slot). — [archive task-scheduler.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/task-scheduler.md); [PR #185](https://github.com/exoharness/exo/pull/185)
- Open scheduler race fixes remain: [#277](https://github.com/exoharness/exo/pull/277), [#278](https://github.com/exoharness/exo/pull/278) (deleted-task resurrection), [#329](https://github.com/exoharness/exo/pull/329) (read-then-write race). — [pulls](https://github.com/exoharness/exo/pulls)
- The current product lists "Scheduled managed-agent deployments (e.g. CMA)" as planned. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)

**Chat gateways (adapters)**
- Archived adapters: `exochat`, `irc`, `whatsapp` (Baileys), `signal` (signal-cli), `discord` (including voice), `slack`, and `agent-cli` (local unix socket). Each runs as a supervised worker process speaking JSONL over stdin/stdout. Inbound messages create a "wakeup" turn. Outbound replies only go through the explicit tool `send_adapter_message`, using a durable outbox (queued → in-flight → delivered/failed, up to 3 attempts). — [archive adapters.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/adapters.md); [archive lifecycles.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/lifecycles.md)
- **No Telegram adapter on main.** A grep of the clone for "telegram" finds nothing. PR #259 "Add Telegram adapter" (long-polling `getUpdates`) has been open since 2026-09-03 with no review comments. — [PR #259](https://github.com/exoharness/exo/pull/259)
- In the current product: "Adapters connect an agent to chat providers like Slack, WhatsApp, and Discord… Adapters run in `--serve` mode". Inline frontmatter configuration is "Planned"; deployments currently come from a separate adapters file. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)

**Observability**
- Native Braintrust tracing: `traceExecutorTurn` and `wrapAnthropic`, plus `crates/executor/src/native/braintrust.rs`. TRACEPARENT and TRACESTATE are propagated into Claude Code. — [responses.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/model-runtime/responses.ts); [claude-code-harness.ts](https://github.com/exoharness/exo/blob/main/exoharness/examples/typescript/claude-code-harness.ts)
- Every LLM response carries a per-message usage and timing record in the event log. Dollar cost is computed "in userspace" from the LiteLLM price database. Usage is "agent-reported telemetry, not an attested ledger". — [cost-tracking.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/design/cost-tracking.md)
- An OpenTelemetry tracing request ([#292](https://github.com/exoharness/exo/issues/292)) is closed. Its resolution was not determined. The `pnpm events:tail` script tails agent events. — [package.json](https://github.com/exoharness/exo/blob/main/package.json)
- Archived adapter health fields are `last_connected_at_ms` and `last_error`. `list_adapter_events` and `list_conversation_events` support introspection. — [docs/SELF-CONTROL.md](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md)

### Inferences
- The `claude-code` harness does not use Claude Code as a long-lived session. Every Exo turn launches a new Claude Code process with `persistSession: false` and a flattened transcript, so Claude Code's own session continuity and `/compact` are not used across turns. Exo has no compaction of its own for this path, so a long-running thread's prompt grows without bound. Whether Anthropic prompt caching stays effective with a single growing user message is not determined.
- Exo's "harness-agnostic" claim is substantively implemented: Codex, Claude Code, Pi, and Cursor adapters all write to one Lingua-formatted event log. This is the layer Saga's option (2) is considering.

### Gaps
- Could not determine whether Claude Code features such as Channels, plugins, CLAUDE.md loading, and `settingSources` behave inside the SDK-spawned process. The harness sets no `settingSources`.
- No first-class sub-agent or multi-agent orchestration API was found. Absence was confirmed by grep only.

## 3. Extension model: plugins, hooks, skills, MCP, custom tools, config

### Takeaway
Exo extends through code *around* the agent: TypeScript harness modules, TypeScript tool modules, client ("frontend") tools fulfilled by the connecting app over HTTP, and MCP servers. It has no Claude-Code-style lifecycle hook system and no plugin marketplace. Skills follow the agentskills.io standard but exist only in the archived agent. Configuration is markdown frontmatter plus YAML environments.

### Cited Findings
- Harness contract: `TypeScriptHarness { tools?, nativeToolApprovals?, reconcileUnresolvedToolCalls?, runTurn(context), resumeTurn?(context) }`. Selected via `harness: ./my-harness.ts`. — [harness/index.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/harness/index.ts); [harnesses.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/harnesses.md)
- The shared turn loop exposes two "hooks": `instructions(context)`, which re-runs every round, and `registerTools(registry, context)`. — [turn-loop.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/model-runtime/turn-loop.ts); [custom-coding-agent tutorial](https://github.com/exoharness/exo/blob/main/website/docs-src/tutorials/custom-coding-agent.md)
- Lifecycle events available to integrators are the event-log kinds (Section 2) plus harness custom events, such as the Claude harness's `claude_turn_started`, `claude_process_starting`, and `claude_process_started`, and `agent_runtime.approval_requested`. They are consumed by watching `/event/watch`, not by registering hooks. — [claude-code-harness.ts](https://github.com/exoharness/exo/blob/main/exoharness/examples/typescript/claude-code-harness.ts); [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Internally, the Claude harness uses only the Agent SDK `PreToolUse` hook, for authorization. — [claude-code-harness.ts](https://github.com/exoharness/exo/blob/main/exoharness/examples/typescript/claude-code-harness.ts). A per-request egress authorization hook is open as [PR #349](https://github.com/exoharness/exo/pull/349).
- Tool implementations can be a "TypeScript tool module" (runs on the runtime host and can exec in the sandbox), a "Client tool" (the connected application), or an "MCP tool". "Harness modules and TypeScript tool modules run as trusted code… there is not a capability sandbox around the module itself." — [harnesses.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/harnesses.md)
- Client tools: Exo emits `tool_requested` and waits. The app posts to `/exo/agent/A/thread/T/turn/TURN/frontend-tool-result`. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Planned but not done: frontmatter tool declarations (today, `frontend_tools` go on each HTTP turn request), environment `tool_modules`, and "Load environment tool implementations in the Codex, Claude Code, and Pi harnesses… [they] do not load the configured TypeScript tool modules". — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- MCP is client-side only (`mcp_servers: [{type: url, name, url, allowed_tools, blocked_tools, permission_policy, tool_policies}]`). "By default, MCP tools require approval." MCP OAuth login is supported through `exo vault secret create global NAME --url …/mcp`. Codex and Claude Code use their native MCP clients inside the sandbox, with placeholder credentials. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md); [vaults.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/vaults.md); [docs/egress.md](https://github.com/exoharness/exo/blob/main/docs/egress.md)
- No feature exposing Exo itself as an MCP server for external clients was found. The only MCP server is the internal `exo_runtime` bridge. — [claude-runtime-tools.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/harness/claude-runtime-tools.ts)
- Skills follow the [agentskills.io](https://agentskills.io) format (SKILL.md with name/description) with progressive disclosure in three stages. Storage is agent artifacts (`skills/index.json`, `skills/<name>.json`). Tools: `install_skill`, `list_skills`, `use_skill`, `read_skill_file`, `uninstall_skill`. "skills published for Claude Code / OpenClaw / Hermes… install here unchanged". — [exoharness/docs/design/skills.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/design/skills.md)
- AGENTS.md: the repo has a contributor `AGENTS.md`. The archived agent's identity prompt tells it to "read and follow any `AGENTS.md` or `CLAUDE.md` in scope", with nested files taking precedence. — [AGENTS.md](https://github.com/exoharness/exo/blob/main/AGENTS.md); [exo/prompts/me.md](https://github.com/exoharness/exo/blob/main/exo/prompts/me.md)
- Archived self-extension: `manage_tool` installs tools from workspace-relative directories or pinned git commits containing `exo-tool.json`, tracked in `tools.lock.json`. Strict JSON-schema validation rejects non-conforming tools. — [archive tools.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/tools.md)
- Configuration format: agent = markdown with YAML frontmatter (`harness`, `model{name, credential, base_url, reasoning_effort}`, `mcp_servers`, `tools`, `resources`, `adapters`); environment = `environment.yaml`; egress policy in JSON, YAML, or TOML. "Unsupported fields are rejected". — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md); [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md); [docs/egress.md](https://github.com/exoharness/exo/blob/main/docs/egress.md)

### Inferences
- For Saga, the extension points that matter are client tools (fulfilled by a sidecar over HTTP) and HTTP MCP servers. Both work with the `claude-code` harness today. TypeScript tool modules do not yet load in the Claude Code, Codex, or Pi harnesses.

### Gaps
- No official list of supported Claude Code plugin or hook passthrough inside the SDK-spawned process. Not determined.

## 4. Autonomy and unattended operation

### Takeaway
Exo is built for headless, server-side operation. `exo run … --serve` exposes an HTTP API with durable turn queuing, cancel, and event replay, and turns keep running after clients disconnect. It has no "loop until done" or Ralph-style mode; a turn ends when the model stops calling tools or `maxToolRoundTrips` is hit. Installation is from source only (Rust plus pnpm). By default Exo wants to own its sandboxes (SmolVM microVMs).

### Cited Findings
- `exo run agent.md --prompt "…"` runs one turn. Without `--prompt` you get a REPL. `--serve` serves over HTTP under `/exo`. For non-loopback binds, use `--auth-file`. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- HTTP flow: `POST …/thread/{id}/turn` returns a receipt once input is accepted. `GET …/event/watch` replays and follows events, and `?after=EVENT_ID` resumes. `POST …/turn/{TURN_ID}/cancel` cancels. "You can stop watching and come back later; the turn keeps running on the server." — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Turn submission options include `idempotency_key` and `attention: wake | interrupt`. Turn control is Run, Cancel, or Suspend. The source comment says these options are "shared by local submissions and remote runtime requests". — [crates/exoharness/src/turn_coordinator.rs](https://github.com/exoharness/exo/blob/main/crates/exoharness/src/turn_coordinator.rs)
- Planned: agent-less routes such as `POST /exo/turn` and plain-string input. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Approvals without a TTY: watch for `agent_runtime.approval_requested`, then `POST …/approval-response {approval_id, approved, allow_for_tool}`. MCP tools default to `always_ask`. Built-in tools default to `always_allow`. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md); [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md)
- Loop bound: `maxToolRoundTrips` caps tool rounds per turn. — [turn-loop.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/model-runtime/turn-loop.ts)
- Archived autonomy prompt rules: "after about three failed attempts on the same blocker, stop and escalate". "When running autonomously with no user attached (scheduled or adapter-triggered work)… keep going on your best judgment, and if you truly cannot proceed, record the blocker clearly… and fail loudly rather than waiting." — [exo/prompts/me.md](https://github.com/exoharness/exo/blob/main/exo/prompts/me.md). Also: "Do not send acknowledgment-only messages… sending a message does not schedule work or keep the turn running." — [exo/harness.ts](https://github.com/exoharness/exo/blob/main/exo/harness.ts)
- The archived agent runs as long-lived host processes: an adapter runner (`exo serve`, lock-guarded, one supervised worker per adapter, exponential-backoff restarts), a scheduler runner, and an optional REPL. A guardian (`exo/scripts/exo-service-guardian`) handles build, restart, and logs. Restarts are drained using marker files (`.exo/exo-adapters.restart`, `.exo/exo-scheduler.restart`). — [archive lifecycles.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/lifecycles.md); [docs/SELF-CONTROL.md](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md)
- "If the runner is down, the agent goes **deaf** (no inbound wakeups), not merely mute". — [archive lifecycles.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/lifecycles.md)
- Install requires building from source: `pnpm install --frozen-lockfile; cargo build -p exo`. "The built-in TypeScript harness constructors resolve bundled runners and modules from the source checkout used to build Exo… Keep that checkout installed". — [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md); [coding-agent-harnesses.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/coding-agent-harnesses.md)
- Sandboxes default to SmolVM. The CLI downloads a checksum-verified SmolVM runtime on first use unless `SMOLMACHINES_NO_DOWNLOAD=1`. Docker, Apple container, Firecracker, `local_process` (no isolation), and hosted backends are alternatives. An existing Docker container can be *attached*. — [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md); [sandboxes.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/sandboxes.md)
- The archived `exo.sh` quickstart requires "Docker running, a Rust toolchain, and Node with pnpm" and mounts the repo at `/workspace/exo`. — [exo/README.md](https://github.com/exoharness/exo/blob/main/exo/README.md)
- Headless provider login: when the keychain store is unavailable, the error says to "use exo provider login <name> --api-key-env <ENV_VAR> for headless access". — [crates/cli/src/providers/oauth.rs](https://github.com/exoharness/exo/blob/main/crates/cli/src/providers/oauth.rs)
- On macOS the vault master key is in Keychain; otherwise it is a file (`master.key`). — [vaults.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/vaults.md); [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md)
- Many docs and tests are macOS-first (Apple container on macOS 26, Lima for Firecracker). "Change `provider` to `docker` on Linux." — [coding-agent-harnesses.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/coding-agent-harnesses.md); [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md)

### Inferences
- First-run dialogs, the problem Saga solved with `claude-baseline.json`, should not arise for Exo's Claude path, because the SDK drives Claude Code non-interactively. That is the same property that moves billing off the subscription (Section 5).
- SmolVM and Firecracker are microVM runtimes and very likely need `/dev/kvm`. Running Exo *inside* a Saga container would mean passing through KVM, using the Docker backend (needs the Docker socket), or using `local_process` (no isolation, and no credential substitution).

### Gaps
- Exo's own behaviour as PID 1 in a no-TTY Docker container (signal handling, log destinations) is undocumented.

## 5. Models and auth/billing

### Takeaway
Exo authenticates models with API keys only. The `claude-code` harness is built on the Claude Agent SDK, which bills per token, and Anthropic's SDK docs forbid third-party products from offering claude.ai login. A community PR adding Claude Max and ChatGPT subscription auth through `CLAUDE_CODE_OAUTH_TOKEN` was never merged. Exo's docs say nothing about Anthropic's April 2026 policy. Running Saga's Claude agents through Exo would move them to API billing.

### Cited Findings
- "The sandbox receives a placeholder in the SDK's API-key variable; the proxy resolves the vault key. **Model authentication supports API keys, not OAuth/subscription caches.**" — [docs/egress.md](https://github.com/exoharness/exo/blob/main/docs/egress.md)
- "Missing model credentials fail instead of falling back to host API keys." — [vaults.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/vaults.md)
- Claude Code setup in Exo uses `exo vault secret create global anthropic --token-env ANTHROPIC_API_KEY --allow-origin https://api.anthropic.com`. — [coding-agent-harnesses.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/coding-agent-harnesses.md)
- Anthropic's Agent SDK docs: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods…" — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- PR #297 "Subscription auth for claude-code and codex harnesses" added `auth_mode: subscription` using `CLAUDE_CODE_OAUTH_TOKEN` for Claude and `auth.json` for Codex. Its author reported a real end-to-end Claude turn "with zero `ANTHROPIC_API_KEY`". It was closed on 2026-09-21 without merging; the author said it was "Opened against the wrong base by mistake". — [PR #297](https://github.com/exoharness/exo/pull/297)
- PR #168 "Codex: support ChatGPT subscription auth with ExoChat" has been open since 2026-07-26. — [PR #168](https://github.com/exoharness/exo/pull/168)
- Providers: Codex with OpenAI; Claude Code with Anthropic; Pi with `provider/model` (a bare name is read as OpenAI); Cursor with `CURSOR_API_KEY`. The basic runtime supports OpenAI Responses, Chat Completions (OpenRouter), and Anthropic. The `braintrust-llm-router` is built with OpenAI, Anthropic, Google, and Bedrock providers. Custom endpoints are set with `model.base_url`. — [coding-agent-harnesses.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/coding-agent-harnesses.md); [responses.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/model-runtime/responses.ts); [Cargo.toml](https://github.com/exoharness/exo/blob/main/Cargo.toml); [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- The landing page claims support for "OpenAI, Claude, Gemini, and local models". — [exoharness.ai](https://exoharness.ai/)
- Cross-model use of the vendor CLIs through a LiteLLM translation proxy is in an open PR. — [PR #301](https://github.com/exoharness/exo/pull/301)
- Cost controls: `maxToolRoundTrips`. "`model.max_output_tokens` is parsed, but the bundled coding harnesses do not yet honor it." There is per-message usage and cost telemetry. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md); [cost-tracking.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/design/cost-tracking.md)
- A grep of the clone for "subscription", "CLAUDE_CODE_OAUTH", "Max plan", "chatgpt", and "console.anthropic" found no statement on Anthropic's April 2026 first-party-only subscription policy. The only subscription statement is the egress.md line above. (Repo grep at commit 423d7d0.)

### Inferences
- Saga's April 2026 tests found two things: `CLAUDE_CODE_OAUTH_TOKEN` leaves Claude Code in API mode (anthropics/claude-code#16238), and Agent SDK sessions bill per token (both recorded in Saga's CLAUDE.md). Exo's Claude path is SDK-based by construction, so it cannot meet Saga's "everything bills to Max" constraint. Even an upstream version of PR #297 would conflict with Anthropic's SDK login prohibition and with Saga's own evidence.
- The cheapest Exo-native options for non-Claude workers are Pi or the basic loop with OpenRouter or a local `base_url`, and Codex with an OpenAI API key. ChatGPT-subscription Codex is not merged.
- No spend-cap or budget-stop feature was found. Cost visibility exists but enforcement does not.

### Gaps
- Not determined whether prompt caching is effective for the Claude harness's flattened transcript, which drives real per-turn cost.

## 6. Security and sandboxing

### Takeaway
Security is Exo's most developed area. It offers microVM sandboxes, proxy-based credential substitution so agents never see real secrets, exact-host egress allowlists, encrypted vaults, and per-tool approval policies. The strongest guarantees (credential substitution and enforced egress) require SmolVM or Firecracker. Docker sandboxes reject credential bindings.

### Cited Findings
- Backends: smolvm (default), firecracker, docker, apple_container, local_process ("Commands run on the host without isolation"), daytona, e2b, sprites, vercel, aws_agentcore. — [sandboxes.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/sandboxes.md)
- Credential substitution works like this: "Agents get placeholder credentials like `OPENAI_API_KEY=exo_egress_…`. Exo substitutes the real credential outside of the sandbox, on requests to permitted destinations." It "require[s] SmolVM or Firecracker". — [vaults.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/vaults.md); [sandboxes.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/sandboxes.md)
- "Docker and Apple Containers currently reject credential bindings." E2B and Daytona reject credential bindings and limited networking. — [docs/egress.md](https://github.com/exoharness/exo/blob/main/docs/egress.md)
- Firecracker egress: it redirects guest TCP 80/443 and DNS through the proxy and rejects IPv6 and QUIC. It pins upstream IPs, validates TLS, requires matching SNI and Host, does not follow redirects, and caps requests at 8 MiB. A credential's allowed hosts never expand when the sandbox's allowlist does. — [docs/egress.md](https://github.com/exoharness/exo/blob/main/docs/egress.md)
- Network policy `networking.type` is `limited`, `unrestricted`, or `disabled`, with `allowed_hosts` and `allowed_tcp_ports`. "Networking is unrestricted by default". — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Vaults: secrets are encrypted on disk, with per-secret `--allow-origin` and `--allow-url` destination policies. Precedence is attached > personal > global. Use a dedicated adapter vault "so the agent itself can't use the bot's credentials". — [vaults.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/vaults.md); [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Permissions: `permission_policy` and `tool_policies` (`always_allow` or `always_ask`), `allowed_tools`, and `blocked_tools`. Policies cover Claude Code's native tools through `PreToolUse`. "Codex and Cursor currently reject native `always_ask` policies". — [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md)
- Trust boundary: harness and tool modules are trusted host code. "Sandbox network policies… do not constrain arbitrary host-side code in a module". — [harnesses.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/harnesses.md)
- Remote server auth includes OIDC (`crates/executor/src/native/remote/oidc.rs`) and session design. — [remote-server.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/design/remote-server.md). Fuzz targets exist for the Firecracker protocol. — [fuzz/](https://github.com/exoharness/exo/tree/main/fuzz)
- Snapshot limits: "A sandbox using credential substitution therefore cannot currently use these snapshot paths." — [sandboxes.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/sandboxes.md)

### Inferences
- Exo's model, a trusted host runtime that creates and controls sandboxes, puts sandbox-launch authority in Exo's own process. In Saga that authority belongs to Heimdall, and Odin never gets the Docker socket (Saga CLAUDE.md). Adopting Exo as a launcher would move Saga's security boundary. Exo's proxy credential substitution is stronger than Saga's iptables allowlist for secret confidentiality, but only on KVM-backed backends.

### Gaps
- No independent security audit was found.

## 7. Fit for Saga

### Takeaway
(a) **Odin on Exo:** technically feasible, but it breaks Saga's billing constraint (API per-token via the Agent SDK). It also gives up Claude Code session continuity and the Telegram Channels path. Exo has no Telegram adapter on main and no conversation compaction. It would gain a clean HTTP turn-injection API that replaces `tmux send-keys`. Not recommended while the Max-only constraint holds.
(b) **Dvergr on Exo:** viable only for non-Claude workers (Pi, Codex, or basic with API keys or local models). There is no Ralph-style loop or post-turn hook; both would be rebuilt with an external driver that watches `/event/watch`. Startup is heavy: build from source, plus a runtime that wants to own sandboxes.
(c) **Patterns:** this is Exo's main value to Saga. The durable turn queue with idempotency and interrupt, structured wakeups, an explicit outbound tool with a durable outbox, scheduler fire durability, host events in the same log, a small always-injected memory, and its compaction rules are all directly portable to Saga on Claude Code.

### Cited Findings and analysis

**(a) Could Odin run on it?**
- Turn injection without tmux is possible. External events can be posted as turns with `POST /exo/agent/A/thread/T/turn` and `{"input":{"role":"user","content":"…"}}`. Turns queue durably per thread. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md). The submission options `idempotency_key` and `attention: interrupt` exist. — [turn_coordinator.rs](https://github.com/exoharness/exo/blob/main/crates/exoharness/src/turn_coordinator.rs). Archived adapters already turn inbound messages into "wakeup" turns, serialized per conversation by a file lock. — [conversation_wakeup.rs](https://github.com/exoharness/exo/blob/main/crates/executor/src/native/conversation_wakeup.rs)
- Outbound and event export: `GET …/event/watch?after=EVENT_ID` streams the thread's events (turn_started/ended, tool_requested/result, messages). A ratatoskr-like sidecar could republish them to MQTT. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- File inboxes and outboxes as tools: as *client tools*, the sidecar fulfils `tool_requested` events through `frontend-tool-result`; these are bridged into Claude Code through the `exo_runtime` MCP server. - Lost relative to today:
  - Subscription billing. The Claude path is Agent SDK with API keys only. — [docs/egress.md](https://github.com/exoharness/exo/blob/main/docs/egress.md); [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

  - Compaction. The basic loop has none and PR #170 is unmerged. — [PR #170](https://github.com/exoharness/exo/pull/170)
  - Telegram. There is no adapter on main (PR #259 is unreviewed), and adapters belong to the archived agent or "planned" inline config. — [PR #259](https://github.com/exoharness/exo/pull/259); [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
  - Crash recovery mid-turn. "Claude Code… end an interrupted turn as failed". — [harnesses.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/harnesses.md)
- Billing consequence (inference): every Odin turn would bill Opus at API rates, with a growing transcript re-sent each turn. That is incompatible with the hard constraint. A non-Claude model would avoid Anthropic billing but changes Odin's model, which is outside the current design.
- As a reference for option (1), a standalone custom Odin harness, Exo is a strong blueprint. Its harness contract (`runTurn`/`resumeTurn` plus an event log) and HTTP turn API are exactly what an extracted Odin would need. Those parts could be built on the Anthropic API, but that is also per-token (inference).

**(b) Could a dvergr run on it?**
- Post-turn MQTT publishing: there is no user-level Stop or post-turn hook. Equivalents are (i) a sidecar watching `/event/watch` for `turn_ended` or `tool_result` and publishing to MQTT, or (ii) a custom TS harness wrapping `runTurn`. — [data-model.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/data-model.md); [harness/index.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/harness/index.ts)

A Ralph-style loop would be an external driver posting the next turn, optionally with guidance text. - Container-friendly startup: weak. It defaults to SmolVM with an auto-download. — [managed-agents.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/managed-agents.md). Digest-pinned devbox images (`ghcr.io/exoharness/{codex,claude-code,pi}-devbox`) exist for the *sandbox*, not for Exo itself. — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md)
- Harness-agnostic relevance to option (2): Exo already normalizes Codex, Claude Code, Pi, and Cursor into one event schema with a common approval mechanism, and lets a thread switch harness while keeping history (`--harness pi --model …`). — [agent-definition.md](https://github.com/exoharness/exo/blob/main/website/docs-src/agent-definition.md); [harnesses.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/harnesses.md). Saga could copy that event schema for its MQTT status and journal topics without adopting Exo.
- Deployment topology choices (inference):
  - Exo as a central runtime on the VM, owning sandboxes. This overlaps or replaces Heimdall, and its Docker backend would need the socket.
  - Exo inside each dvergr container with `local_process`. The container is the isolation; there is no credential substitution; it is heavy.
  - Exo attaching to Heimdall-launched containers through `sandbox attach --sandbox docker --external-id`. Exo still needs Docker access. — [archive lifecycles.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/lifecycles.md)
  None fits cleanly with "Heimdall is the only thing with Docker".

**(c) Patterns worth adopting even on Claude Code (named, with file references)**
1. **Durable turn queue with idempotency key and wake/interrupt attention** — [crates/exoharness/src/turn_coordinator.rs](https://github.com/exoharness/exo/blob/main/crates/exoharness/src/turn_coordinator.rs). Ratatoskr could keep an on-disk queue of nudges keyed by MQTT message ID to deduplicate, and mark operator-urgent items "interrupt" (for example, send Escape before injecting) while everything else is "wake" (inject only when idle).
2. **Structured wakeup envelope with a reply contract** — `compose_inbound_wakeup_prompt` in [crates/executor/src/native/adapter/runtime.rs](https://github.com/exoharness/exo/blob/main/crates/executor/src/native/adapter/runtime.rs), plus the per-conversation wakeup file lock in [conversation_wakeup.rs](https://github.com/exoharness/exo/blob/main/crates/executor/src/native/conversation_wakeup.rs). Replace free-text tmux nudges with a fixed header (source, adapter or topic, target, sender, "if you answer, reply via X with target Y"), and serialize injections per pane.
3. **Explicit outbound plus durable outbox** — "model text is never automatically posted back externally — `send_adapter_message` is always an explicit decision". Delivery states are queued, in-flight, delivered, or failed, with 3 attempts. — [docs/SELF-CONTROL.md §5](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md); [archive adapters.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/adapters.md). For Odin's guidance to dvergar and Telegram replies, a file outbox with state transitions makes delivery auditable.
4. **Scheduler fire durability** — record the fire, prompt included, *before* the wakeup and clear it after. Delivery is at-least-once keyed by (task, slot), with an anchored grid, `missed: skip|once|all`, and `@at` one-shots that stay listed after completion. — [archive task-scheduler.md](https://github.com/exoharness/exo/blob/main/website/docs-src/archive/concepts/task-scheduler.md); [PR #185](https://github.com/exoharness/exo/pull/185). This applies directly to Odin's periodic check-ins and stuck-dvergr sweeps.
5. **Host events in the same immutable log** — `host_reboot`, `adapter_runner_started` ("a start without a preceding `host_reboot` implies a crash"), `adapter_runner_draining`, `rebuild_and_restart_exo`. — [docs/SELF-CONTROL.md §2](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md). Heimdall launch results, container exits, keepalive auth refreshes, and ratatoskr restarts could become journal events Odin reads.
6. **Drain markers plus reboot-notice wakeup** — restarts drain through marker files. A reboot notice wakes the agent after restart so it can announce it is back; stale notices are discarded after 15 minutes. — [docs/SELF-CONTROL.md §1](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md). This applies to Odin container restarts and credential re-bootstraps.
7. **Small always-injected memory with IDs, capped, no embeddings** — `remember` and `forget`, stored as one artifact. — [docs/SELF-CONTROL.md §2](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md); [exo/tools/memory-tools.ts](https://github.com/exoharness/exo/blob/main/exo/tools/memory-tools.ts). This is a good fit for Odin's "principles" with stable IDs so Mimir can cite and retire them.
8. **Todo list re-injected every turn** — [exo/tools/todo-tools.ts](https://github.com/exoharness/exo/blob/main/exo/tools/todo-tools.ts); [exo/harness.ts](https://github.com/exoharness/exo/blob/main/exo/harness.ts).
9. **Large tool output to artifact plus preview** — [exoharness/typescript/harness/tools.ts](https://github.com/exoharness/exo/blob/main/exoharness/typescript/harness/tools.ts). For example, ratatoskr could write full dvergr journals to files and inject only previews and paths.
10. **Append-only event log as truth; prompt as a derived view; UUIDv7 cursors with `?after=` replay** — [data-model.md](https://github.com/exoharness/exo/blob/main/website/docs-src/architecture/data-model.md). Saga's MQTT topics could carry monotonic UUIDv7 event IDs so Odin and Grafana can resume from a cursor after downtime.
11. **Safe compaction cut rules**, if Saga builds its own Odin harness: cut only at `turn_ended` where every earlier turn has closed; age out orphaned turns after 8; trigger on input occupancy including cache reads, not on `prompt_tokens`. — [PR #170](https://github.com/exoharness/exo/pull/170)
12. **Autonomy prompt rules** — escalate after about 3 failed attempts on one blocker; when unattended, "fail loudly rather than waiting"; no acknowledgement-only messages. — [exo/prompts/me.md](https://github.com/exoharness/exo/blob/main/exo/prompts/me.md); [exo/harness.ts](https://github.com/exoharness/exo/blob/main/exo/harness.ts). These suit both Odin and dvergr prompts.
13. **Self-map file** — `exo/SELF.md` is a compact, navigational map the agent reads before self-maintenance. — [exo/SELF.md](https://github.com/exoharness/exo/blob/main/exo/SELF.md). Relevant to Eir and to Odin's understanding of Saga's own infrastructure.
14. **Health fields and a diagnosis ladder** — `last_connected_at_ms` and `last_error`, then event history, then logs, then restart. — [docs/SELF-CONTROL.md §3](https://github.com/exoharness/exo/blob/main/docs/SELF-CONTROL.md). Applicable to ratatoskr, keepalive, and the Telegram channel.
15. **Proxy credential substitution with per-secret destination allowlists** — [docs/egress.md](https://github.com/exoharness/exo/blob/main/docs/egress.md). This could be a future hardening for dvergr Gitea tokens. It needs a host-side proxy and is not Docker-native in Exo.
16. **Per-message usage records in the event log, cost computed outside the trusted core from the LiteLLM price DB** — [cost-tracking.md](https://github.com/exoharness/exo/blob/main/exoharness/docs/design/cost-tracking.md). Useful if Saga ever runs non-Max harnesses.

### Inferences
- Exo's best fit for Saga is as a design reference for Saga's own harness-agnostic layer and a future custom Odin harness, not as a runtime to adopt. Its Claude path conflicts with the billing constraint. Its chat, scheduler, and memory features are archived or planned. Its sandbox ownership model collides with Heimdall.

### Gaps
- Not tested: whether Claude Code Channels (Telegram) can run under the SDK-spawned process in Exo's sandbox.
- Not determined: actual latency and cost of the Claude harness on long threads.

## 8. Risks: bus factor, stability, breaking changes, licensing, policy, lock-in

### Takeaway
High bus-factor and stability risk: two maintainers, no releases, explicit no-back-compat policy, a major product pivot five months in, and repeated renames. Licensing risk is low (MIT). Policy risk for Claude use is high: API-key-only, plus Anthropic's SDK login prohibition. Model lock-in is low, but the event format ties you to Braintrust's Lingua.
